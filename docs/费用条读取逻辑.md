# 费用条读取逻辑（实测版 v1）

> 数据来源：`Arknights 2026.10.02 - 17.08.21.04.mp4`
> 2560x1600 @60fps、H.264 SDR、窗口模式；全程 2 倍速，含 6 段满费、多次暂停与子弹时间。
> 逐帧特征表：`docs/v2_frames.csv`（3401 帧，含 fill / grey146 / grey88 / bar_state / run_state）。

---

## 1. 结论先行：满费判定用「出现 MAX」，不要用「条走满」

实测 6 次进入满费，进入前几帧的填充宽度（条槽宽 241px，每逻辑帧 8px）：

| 进入时刻 | 进入前 4 帧 fill (px) | 是否渲染出满格 240 |
| --- | --- | --- |
| 9.333s | 207, 215, 223, **232** | 否 |
| 21.117s | 207, 215, 223, **232** | 否 |
| 29.900s | 207, 215, 223, **232** | 否 |
| 39.133s | 215, 223, 232, **240** | 是，仅 1 帧 |
| 51.317s | 207, 215, 223, **232** | 否 |
| 0.000s | 录像开始时就已满费 | — |

6 次里有 5 次停在第 29 帧的 232px（96.7%）就直接翻成 MAX，只有 1 次渲染出 1 帧满格。

结论：

- 判据不能写成 `fill == bar_w`，会漏判。
- 判据 = 是否进入 MAX 态（整条均匀灰 146 覆盖）。
- 这比「回费技能提前补满」的理由更硬：即使没有任何提前补费，常规回费也不会稳定渲染满格。

## 2. 费用条的 5 种像素形态

ROI：右下角条槽，2560 宽窗口下为 `x = 2319..2559`（241px）、`y = 1236..1252`。
取中间 6 行（y 1242..1247）逐列中位数，得到一维信号 `row[0..240]`，下面数值都基于它。

| 形态 | 判据 | 实测值 | 含义 |
| --- | --- | --- | --- |
| TRACK 正常充电 | 左端起连续 `>=240` 的像素数 = fill | 白色填充恒为 **255**；未填充轨道渐变 **52~69** | 有效相位读数 |
| MAX 满费 | `abs(v-146)<=10` 的像素数 `>=150` 且 `fill<=4` | 整条**恰好 146**（±0），另有 MAX 字形（笔画在 150~255 间脉冲） | 满费 |
| MAX_FADE 退出过渡 | `abs(v-88)<=8` 的像素数 `>=150` 且 `fill<=4` | 整条**恰好 88**，持续 **14 帧** | 不可当作相位 0 |
| EMPTY 空条 | `fill<=4` 且既非 146 也非 88 | 轨道渐变 **53~68** | 相位 0，或满费标签已超时 |
| 遮挡/异常 | 以上都不满足 | 1132 个 `fill>=20` 的帧里只有 7 帧轨道亮度 >100，**没有一帧 >240** | 用模型拟合剔除 |

关键数字：

- 白色填充 = 255、轨道 = 52~69，差距极大，**阈值 240 非常安全**。
- MAX 底色恒为 **146**：6 段满费、47 秒不同场景下都精确等于 146，说明它是不透明覆盖层，不是半透明叠加。
- MAX 字形比灰底晚 1 帧出现（`grey146=240` 那一帧还没有字），**所以用灰底判满费比识别 MAX 三个字母更早也更稳**。

## 3. 帧率与倍速：条与逻辑帧的定量关系

60fps 采集下，逐帧统计 fill 从满回绕到 0 的间隔：

```
30, 30, 30, 30, 30, 30, 30, 30, 30, 29, 31, 30, 30, 30, 30, 30, ...
```

- **一个费用周期恒等于 30 个逻辑帧**；2 倍速下 1 显示帧 = 1 逻辑帧，所以周期 = 30 显示帧。
- 偶发 29/31 抖动来自游戏内部定点累加器的边界效应（与参考项目 fp24 的分析一致），平均正好 30。
- 每逻辑帧前进 `条槽宽 / 30` px（本例 8px），于是：

```
Δ逻辑帧 = Δfill / (条槽宽 / 30)
```

这就是「费用条动的时候看费用条」的完整实现，天然免疫 1x / 2x / 子弹时间。

## 4. 满费期间相位的行为（很重要）

1. **MAX 期间相位被钉在 0**：退出满费后条从 0 重新涨（实测 fill = 7, 16, 24, 32, 41...，每帧 +8）。
   退出时应直接 `acc = 0` 重新锚定，不要让相位穿越 MAX 传递。
2. **MAX 标签会超时消失**：15.750~15.967s 是 88 灰态，15.983s 起变成纯暗 EMPTY，而此时游戏仍暂停、DP 仍是 99。
   也就是说 EMPTY 既可能是「相位 0」也可能是「满费但标签已消失」。
   → 不能只靠形态区分，**要用 fill 连续为 0 的帧数区分**：真相位 0 只会持续 1~2 帧就开始涨。
3. **满费退出会先经过 14 帧的 88 灰态**，这 14 帧的 fill 读数同样是 0，也不能当相位 0 用。

## 5. 倍速 / 暂停按钮的读取

ROI（2560 宽窗口）：暂停键 `x=2300..2499, y=40..199`；倍速键 `x=2080..2279, y=40..199`。

**按钮有「亮」「暗（半透明）」两种渲染**，暗态下整个控件半透明、能透出背后场景，亮度阈值法会失效，必须用形状特征。

暂停键形状特征（实测 11/11 正确）：

```
取 ROI 行 y=38..48 这条带
thr = median(ROI) + 0.35 * (max(ROI) - median(ROI))
feature = 条带内 > thr 的像素数

feature ≈ 136~139  ->  单三角 ▶   ->  已暂停（点它恢复）
feature ≈ 526~530  ->  双竖条 ❚❚  ->  正在运行（点它暂停）
```

两种形态差约 4 倍，亮态暗态都成立，很稳。

**判据带滞回**（`geometry.PAUSE_RUN_RATIO = 0.20` / `PAUSE_STOP_RATIO = 0.11`）：
占比 >= 0.20 判「运行中」，<= 0.11 判「已暂停」，中间那条带里**沿用上一拍**。
实测三个录像的两簇分别是 0.078 和 0.245，中间带里全是按钮淡入淡出的过渡帧；
用单门限（0.15）会让状态在那儿来回翻。

倍速键：

```
有数字（笔画在 ROI 上部 y=18..60） -> 1X / 2X，具体用模板匹配区分（1 和 2 笔画数不同）
无数字（只有中部 y=50..82 的箭头）-> 子弹时间 >>>，不显示倍速，必须沿用上一次已知倍速
```

实测「无数字」共 12 段，其中 6 段与按钮暗态重合。**暗态 ≠ 暂停**（33.2s 是暗态 + ❚❚ + 正在跑）。

## 6. 状态机与逐帧计数伪代码

**一条铁律：全局帧数只由费用条的像素决定。** 倍速键、暂停键只用来回答「什么时候可以不看条」。

```
每帧:
    row      = 费用条 ROI 逐列中位数
    fill     = 左端起连续 >=240 的像素数          # 0..bar_w
    grey146  = count(|row-146| <= 10)
    grey88   = count(|row- 88| <= 8)
    state    = MAX / MAX_FADE / TRACK / EMPTY

    # 暂停键：形状占比带滞回（>=0.20 运行中、<=0.11 已暂停、中间沿用上一拍，见第 5 节）
    running  = ...

    if 不在关卡里（一段时间没再见过费用条）:
        delta = 0                                  # 关卡外一帧都不记
    elif state in (MAX, MAX_FADE):                 # 满费：条被画出来 = 一定在关卡里
        if not running:            delta = 0       # 暂停
        elif 倍速键上没数字:        delta = 0       # 冻结，绝不猜一个倍速
        else:                      delta = 30 * m * dt
    elif not running and state == EMPTY:
        delta = 0                                  # 条没画出来 + 暂停
    else:
        delta = 相位重同步(fill)                    # 像素通道：整数逻辑帧，与倍速无关
```

三条路子：

- **像素通道**：条画着填充（含一费开头那两帧的 0 宽平段）→ 数出条走出来的整数逻辑帧。
  **和倍速完全无关**：1X / 2X / 0.2X / 子弹时间都不用读倍速，`_resync` 自己会挑出前进帧数
  （因为一费恒为 30 逻辑帧，倍速只改变每秒有多少逻辑帧，不改变条本身一格走多少像素）。
- **满费挂钟通道**：**只在 MAX / MAX_FADE**。相位被游戏钉在 0，像素里没有任何时间信息，
  只能按 `30 × m × dt` 估（`m` = 倍速键上那个数字，所以 1X 给 30 帧/秒、2X 给 60 帧/秒）。
  数字没画出来（暂停菜单 / 拖干员时的按钮）就**冻结**，不猜 ——
  「没数字」只能推出「不知道倍速」，推不出「0.2 倍速」（暂停菜单里也只剩三条箭头）。

  代价：满费 + 拖干员（0.2 倍速）那段会冻结、少记几帧到几十帧。
  这是**故意**的：猜 1 倍速会多记 5 倍，猜 0.2 倍速在真的 1 倍速时会少记 5 倍，
  两种都比「冻结」错得离谱。
- **冻结**：以上都不成立 → `delta = 0`。

必须接受的事实：**条冻住的那段时间，像素里不存在任何时间信息**，
满费段只能给到 ±1~2 帧的挂钟估算精度。

### 为什么「条不可读就按 1 秒 30 帧涨」是错的

1. **`EMPTY` 不能算「在关卡里」**：主菜单 / 仓库 / 编队 / 关掉结算 / 切场景读出来全是 EMPTY，
   关卡内的「0 费」也是 EMPTY，像素上完全一样。旧逻辑在这些帧上走挂钟通道，
   于是「不在关卡里也在一秒 30 帧地涨」。
   实测：一段 4 秒的「1-7 关卡选择」录屏凭空记了 217 帧；本机 obs 录像里
   空条帧也被凭空记了 15 帧。现在 EMPTY 只能走像素通道（相位对不上就冻结）。
2. **挂钟通道必须乘倍速，而倍速来自倍速键**：倍速读错一倍，整段就错一倍。
   实测「一费 30 帧」被算成 **62 帧**，就是旧版在倍速读不出来时默认 2X 造成的。
   现在读不出来就冻结 —— 宁可少记，不要凭空多记。

### 怎么验证「一费 = 30 帧」

- `tools/check_speed_mix.py`：把 1X / 2X / 0.2X / 暂停 / 满费 / 关卡外混在一起喂给状态机，
  和**算出来的精确真值**比总帧数（现在 9 个场景全部 ±1 帧以内）。
- `tools/check_bar_linearity.py`：不需要知道倍速，直接卡「这一段记的帧数」和
  「费用条自己走了多少像素」是否对得上 —— 记多了、记少了都会被抓出来。
- `run_reader.py` 跑完打印的「实测帧率」：像素通道累计逻辑帧 / 累计等效挂钟秒数，
  正确时应正好等于 30.000（= 一费一秒）。

## 7. 已知坑（本机实测踩到的）

1. 满费判据用 `fill == 满格` 会漏判（见第 1 节）。
2. 满费退出有 14 帧 88 灰态，会被误读成相位 0。
3. MAX 标签会超时消失，出现「EMPTY 但 DP 仍是 99」的形态。
4. MAX 期间相位钉在 0，退出后从 0 重锚，不要做相位穿越。
5. 暂停/倍速按钮有亮/暗两种渲染，亮度阈值法失效，必须用形状特征。
6. 子弹时间 >>> 不显示倍速数字，必须缓存上一次倍速。
7. ffmpeg 的 crop 会静默 clamp：`x + w > 帧宽` 时自动左移 x（本次把 2200 改成了 2160），
   导致两次裁剪对不上、白条起点差 40px，排查了很久。**ROI 不要越界，并断言裁剪参数。**
8. ROI 必须按窗口尺寸实时计算（用户会改窗口大小/位置），条槽右端锚定窗口右边缘：
   2560 宽时 = 240px、1920 宽时 = 180px，即 `bar_w = round(180 * W/1920)`（宽高比 > 16:9 时用 H/1080）。
9. **满费期间相位被钉在 0，退出后条从 0 重新涨** —— 所以满费段不要去「推进累加器」，
   冻结相位、等条回来时用相位重同步重新对上就行（上一拍相位 > 0.75 时允许跨回费边界）。
10. **HDR / PQ 采集**：UI 白从 255 掉到 ~122，所有绝对亮度阈值都失效。
   费用条走 features 的「亮度自适应」还原（第 10 节）；
   倍速键的箭头判据也从「绝对 ≥200」改成「本帧白电平的相对阈值」——
   绝对阈值在 HDR 录像上命中率是 0.0000，子弹时间永远认不出来。
11. **倍速键上没数字不等于 0.2 倍速**：暂停菜单里也只剩三条箭头（实测 23.53 录像全程如此）。
   所以「没数字」只能推出「这一刻不知道倍速」，不能据此把速率除以 5 ——
   5 倍的系统偏差比不计数严重得多。

## 8. 暂停键图标会「闪」：挂钟通道必须先确认

**现象（实测）**：游戏暂停时，右上角的「继续」按钮（▶）会以 **2~3 帧**为单位闪回「运行中」的
双竖条形状。一段 76 秒的全程暂停录像里闪了 28 次；逐帧核对过：静止时形状占比 0.062，
闪的那两帧是 0.2378 —— 和真的在跑时一模一样，用阈值分不开。

**后果**：闪的那几帧会被判成「运行中」，而满费时费用条正好不可读，于是走挂钟通道 →
每次闪凭空多 1 帧。76 秒下来计数器多算了 **30 帧**（0.4 帧/秒），肉眼完全看不出来。

**现在的规则**（`state.py` 的 `Counter._clock_gated`）：

| 条件 | 行为 |
| --- | --- |
| 条不可读 + 刚从暂停回来 + 该状态还没连续 5 帧 | `delta = 0`，挂钟时间先攒进 `clock_wait` |
| 连续 5 帧确认（或本来就在跑） | `delta = rate*dt + clock_wait`，**一次性补上**，真实满费不丢帧 |

只在「刚从暂停回来」时才要求确认，这一点很关键：正常打球时一直在跑，条一变满费就立刻照常
补帧；而闪烁一定发生在暂停期间（前面有一串暂停帧），所以它一定躲不过确认。

**为什么不做通用的「暂停状态去抖」（踩过的坑）**：直接给运行/暂停标志加「必须连续保持 N 帧
才算数」的规则，会让「快速暂停 → 继续 → 再暂停」整段识别不出来 —— 一旦读数在切换期间抖动、
每一段都短于 N 帧，状态就永远攒不满、卡死在原值上。现在这套写法**一行都没碰像素通道**：
暂停时费用条照样能读到（实测暂停中 `fill=57 / TRACK`，条只是不动），
条不动 → 像素通道自然给 0 帧，识别速度不受任何影响。

**验收标准**（`tools/check_state_synth.py` 之外的三个手测）：

1. 暂停 60 秒 → 帧数必须一动不动（旧逻辑约涨 24 帧）。
2. 运行中满费 180 帧 → 必须精确算满 180（回填保证不丢）。
3. 暂停 → 继续且费用条可读 → 像素通道零延迟（不应出现 `clock-wait`）。

## 9. 关卡判定：只有「费用条被画出来」才算在关卡里

**现象（录屏实测）**：PC 窗口模式录整个桌面时，主菜单 / 仓库 / 编队 / **关卡选择界面**里
费用条根本不在画面上，读出来是 `EMPTY`。旧逻辑在 `EMPTY` 帧上照走像素 / 挂钟通道，
于是一段 4 秒的「1-7 关卡选择」录屏里凭空记了 **217 帧**（≈7.2 秒游戏时间）。

**规则**（`state.py`）：只有下面三种状态算「费用条被画出来了」：

| 状态 | 含义 | 算不算在关卡里的证据 |
| --- | --- | --- |
| TRACK | 条在推进 | 算 |
| MAX | 满费（整条灰底 + MAX 字样）| 算 |
| MAX_FADE | 满费退出的过渡（88 灰）| 算 |
| EMPTY | 条槽里没有填充 | **不算** |

`EMPTY` 必须不算：关卡内「0 费」和关卡外「根本没有条」在像素上完全一样。
连续 `BATTLE_HOLD_FRAMES = 120` 帧（1~2 秒 @60Hz）没见过费用条就判「不在关卡里」：
`delta = 0`，并且 `resync()` 重新锚定，这样下一局开局不会把上一局的余量接上去。
120 帧的滞回是用来兜住关卡内的短暂读不到（切场景、被部署动画挡住）。

同一段录屏：改前 217 帧 → 改后 **0 帧**。

## 10. HDR / PQ 采集：白电平从 255 掉到 122

**实测（两段 NVIDIA 录屏，`hevc Main 10, yuv420p10le, smpte2084`）**：

| 画面元素 | SDR 录像 | HDR 录像 |
| --- | --- | --- |
| 填充白 | 255 | **122** |
| 轨道灰 | 55..68 | 51..58 |
| 满费灰底（对应 146）| 146 | **94** |
| 满费退出过渡（对应 88）| 88 | ~70 |

暂停键 / 倍速键不受影响（它们本来就用相对阈值）；费用条的判据全是绝对阈值
（250 / 146 / 88），于是 HDR 下永远 `EMPTY` → 状态机退回挂钟通道 →
画面上的表现就是「不看条了，按 1 秒 30 帧瞎涨」。而且 94 正好落进「88±10」区间，
真正的满费会被读成 `MAX_FADE`。

**规则**（`features.py`）。先判断这一行是不是「整体被压暗」（`_dim_anchor`，白电平取 99 分位）：

| 行内白电平 | 判断 | 处理 |
| --- | --- | --- |
| < 100 | 关卡外的暗场景（实测整行 9..24），不是 HUD | 不还原 |
| 100 .. 149 | HDR 那种被压暗的 HUD | 还原 |
| >= 150 | SDR 的另一种渲染（蒙遮罩的半透明白 151..165、满费退出时刻的亮字 154）| 不还原 |

要还原时分两路走，只用一种一定有一头是错的：

| 判据 | 怎么还原 | 为什么 |
| --- | --- | --- |
| 填充（白）| 按白电平等比抬亮 `x * 255 / hi` | 填充就在白电平附近；等比抬亮后阈值等价于 0.965 x 白，边界最稳 |
| 灰底（146 / 88）| PQ 反变换到亮度 → 除以白电平 → sRGB（`restore_pq_row`）| 灰底在中间灰度：等比抬亮会把 94 抬成 197，两个灰底判据都命中不了；PQ 反变换把 94 还原成 ~146、70 还原成 ~88 |

白电平是**逐帧测**的，所以换 HDR 亮度档 / 换 SDR 白电平都不用改常数；SDR 画面白电平 = 255，
判据自动退化成恒等变换，已标定过的画面逐像素和以前一样（`docs/v2_frames.csv` 逐帧对齐 0 差异）。

## 11. 录整个桌面时 ROI 要平移：--client / --roi-offset

NVIDIA 录屏录的是整个桌面（2560x1600，含标题栏和任务栏），而游戏客户区是
2558x1440、原点在 `(16, 45)`。ROI 是按「客户区尺寸 + 客户区原点」定的，所以抽流时要交给读取器：

    python run_reader.py "<录像.mp4>" --client 2558x1440 --roi-offset 16,45

不写这两个参数，ROI 会按 2560x1600 算、整体偏掉（垂直差 45px，读到的全是背景）。
`geometry.reframe_layout()` 把三个 ROI 整体平移再按画面尺寸裁掉越界部分 ——
录桌面时右边缘会被裁掉约 14px，条可见宽 226px（真实 239.81px），
计数器用 `Counter(visible_w=...)` 按真实宽度算、画出来才截到可见段。

## 12. 测试用：手动「暂停计数」开关

前端的「暂停计数 (P)」是人工开关，和游戏自己的暂停无关：
按下去以后数字**一动不动**（读数、预览照常刷新），方便对着录像 / 轴逐段核对。
放开时不是把按住的那段补回来，而是 `resync(keep_battle=True)` 重新起锚：
按住的一段既不会事后计入、数字也不会跳。为什么不补：按住期间游戏可能经历
暂停 / 满费 / 切出屏幕，算不出一个可靠的正确值，猜一个反而比不记更差。
`tools/check_speed_mix.py` 里的「手动暂停计数」用例就是钉这两件事的。
