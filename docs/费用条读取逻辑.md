## 1. 结论先行：满费判定用「出现 MAX」，不要用「条走满」

实测 6 次进入满费，进入前几帧的填充宽度（条槽宽 241px，每逻辑帧 8px）：

| 进入时刻 | 进入前 4 帧 fill (px) | 是否渲染出满格 240 |
| --- | --- | --- |
| 9.333s | 207, 215, 223, **232** | 否 |
| 21.117s | 207, 215, 223, **232** | 否 |
| 29.900s | 207, 215, 223, **232** | 否 |
| 39.133s | 215, 223, 232, **240** | 是，仅 1 帧 |
| 51.317s | 207, 215, 223, **232** | 否 |
| 0.000s | 录像开始时就已满费 | — |

6 次里有 5 次停在第 29 帧的 232px（96.7%）就直接翻成 MAX，只有 1 次渲染出 1 帧满格。

结论：

- 判据不能写成 `fill == bar_w`，会漏判。
- 判据 = 是否进入 MAX 态（整条均匀灰 146 覆盖）。
- 这比「回费技能提前补满」的理由更硬：即使没有任何提前补费，常规回费也不会稳定渲染满格。

## 2. 费用条的 5 种像素形态

ROI：右下角条槽，2560 宽窗口下为 `x = 2319..2559`（241px）、`y = 1236..1252`。
取中间 6 行（y 1242..1247）逐列中位数，得到一维信号 `row[0..240]`，下面数值都基于它。

| 形态 | 判据 | 实测值 | 含义 |
| --- | --- | --- | --- |
| TRACK 正常充电 | 左端起连续 `>=240` 的像素数 = fill | 白色填充恒为 **255**；未填充轨道渐变 **52~69** | 有效相位读数 |
| MAX 满费 | `abs(v-146)<=10` 的像素数 `>=150` 且 `fill<=4` | 整条**恰好 146**（±0），另有 MAX 字形（笔画在 150~255 间脉冲） | 满费 |
| MAX_FADE 退出过渡 | `abs(v-88)<=8` 的像素数 `>=150` 且 `fill<=4` | 整条**恰好 88**，持续 **14 帧** | 不可当作相位 0 |
| EMPTY 空条 | `fill<=4` 且既非 146 也非 88 | 轨道渐变 **53~68** | 相位 0，或满费标签已超时 |
| 遮挡/异常 | 以上都不满足 | 1132 个 `fill>=20` 的帧里只有 7 帧轨道亮度 >100，**没有一帧 >240** | 用模型拟合剔除 |

关键数字：

- 白色填充 = 255、轨道 = 52~69，差距极大，**阈值 240 非常安全**。
- MAX 底色恒为 **146**：6 段满费、47 秒不同场景下都精确等于 146，说明它是不透明覆盖层，不是半透明叠加。
- MAX 字形比灰底晚 1 帧出现（`grey146=240` 那一帧还没有字），**所以用灰底判满费比识别 MAX 三个字母更早也更稳**。

## 3. 帧率与倍速：条与逻辑帧的定量关系

60fps 采集下，逐帧统计 fill 从满回绕到 0 的间隔：

```
30, 30, 30, 30, 30, 30, 30, 30, 30, 29, 31, 30, 30, 30, 30, 30, ...
```

- **一个费用周期恒等于 30 个逻辑帧**；2 倍速下 1 显示帧 = 1 逻辑帧，所以周期 = 30 显示帧。
- 偶发 29/31 抖动来自游戏内部定点累加器的边界效应（与参考项目 fp24 的分析一致），平均正好 30。
- 每逻辑帧前进 `条槽宽 / 30` px（本例 8px），于是：

```
Δ逻辑帧 = Δfill / (条槽宽 / 30)
```

这就是「费用条动的时候看费用条」的完整实现，天然免疫 1x / 2x / 子弹时间。

### 3.1 子弹时间（>>>）是**固定** 6 帧/秒，不是「当前倍速 ÷ 5」

拖干员时倍速键变成三条箭头的 `>>>`，游戏被压慢。**压到多慢和倍速设置无关**：
「无视当前倍速将游戏速率调至 1/5」是**绝对**的 1/5 —— 恒为 6 逻辑帧/秒。

实测拿条自己当尺子（条每逻辑帧走 `条槽宽/30` px，像素行程能反推真实速率）：

| 录像 | 倍速设置（倍速键读到的数字）| 子弹时间段 | 条实测速率 |
|---|---|---|---|
| 19-08-39 | 1X（全程）| 5 段，2.1~4.8s | 6.1 / 6.1 / 6.1 / 6.2 / 5.9 帧/秒 |
| 11.01.51.01 | 2X（全程）| 2 段，1.3~1.5s | 6.4 / 6.2 帧/秒 |
| 11.34.28.02 | 2X | 1 段 | 6.1 帧/秒 |

**2X 设置下也是 6 帧/秒，不是 12。** 所以：

- 满费段遇到 `>>>` 直接按 6 帧/秒补，**不要**拿缓存的倍速去除以 5 —— 2X 下那样会多记一倍；
- 条可见时（像素通道）这段照样免疫，倍速根本不用读。

2026-10-06 又复测了一遍（因为「2X 下到底是 6 还是 12」直接决定满费段会不会差一倍），
口径是「拿费用条自己当尺子」—— 条每逻辑帧走 `条槽宽/30` px，和倍速无关：

| 11.01.51.01（倍速键全程画 2X）| 逻辑帧/秒 |
| --- | --- |
| 子弹时间段 896..984 | 6.07 |
| 子弹时间段 1123..1155 | 5.45 |
| 子弹时间段 1717..1740 | 5.00 |
| 子弹时间段 2154..2234 | 5.93 |
| 同一段视频正常 2X 处（10 段）| 60.00（逐段都是） |

子弹时间那几段短（0.4~1.5 秒、只有 2~9 帧），量化误差 ±0.5 帧就是 ±1 帧/秒，
所以 5.0~6.1 这一簇是 6 而不是 12 —— 和 60.00 那条对照，尺子本身误差 <1%。

## 4. 满费期间相位的行为（很重要）

1. **MAX 期间相位被钉在 0**：退出满费后条从 0 重新涨（实测 fill = 7, 16, 24, 32, 41...，每帧 +8）。
   退出时应直接 `acc = 0` 重新锚定，不要让相位穿越 MAX 传递。
2. **MAX 标签会超时消失**：15.750~15.967s 是 88 灰态，15.983s 起变成纯暗 EMPTY，而此时游戏仍暂停、DP 仍是 99。
   也就是说 EMPTY 既可能是「相位 0」也可能是「满费但标签已消失」。
   → 不能只靠形态区分，**要用 fill 连续为 0 的帧数区分**：真相位 0 只会持续 1~2 帧就开始涨。
3. **满费退出会先经过 14 帧的 88 灰态**，这 14 帧的 fill 读数同样是 0，也不能当相位 0 用。

## 5. 倍速 / 暂停按钮的读取

ROI（2560 宽窗口）：暂停键 `x=2300..2499, y=40..199`；倍速键 `x=2080..2279, y=40..199`。

**按钮有「亮」「暗（半透明）」两种渲染**，暗态下整个控件半透明、能透出背后场景，亮度阈值法会失效，必须用形状特征。

暂停键形状特征（实测 11/11 正确）：

```
取 ROI 行 y=38..48 这条带
thr = median(ROI) + 0.35 * (max(ROI) - median(ROI))
feature = 条带内 > thr 的像素数

feature ≈ 136~139  ->  单三角 ▶   ->  已暂停（点它恢复）
feature ≈ 526~530  ->  双竖条 ❚❚  ->  正在运行（点它暂停）
```

两种形态差约 4 倍，亮态暗态都成立，很稳。

**判据带滞回**（`geometry.PAUSE_RUN_RATIO = 0.20` / `PAUSE_STOP_RATIO = 0.11`）：
占比 >= 0.20 判「运行中」，<= 0.11 判「已暂停」，中间那条带里**沿用上一拍**。
实测三个录像的两簇分别是 0.078 和 0.245，中间带里全是按钮淡入淡出的过渡帧；
用单门限（0.15）会让状态在那儿来回翻。

倍速键：

```
有数字（笔画在 ROI 上部 y=18..60） -> 1X / 2X，具体用模板匹配区分（1 和 2 笔画数不同）
无数字 + 中部箭头带锐利发亮        -> 子弹时间 >>>：速率是**确定的 6 帧/秒**
                                      （与倍速设置无关，见 3.1），不是「沿用上次倍速」
无数字 + 箭头带也糊平（没对比度）  -> 按钮淡出 / 被遮罩：这一刻倍速未知，沿用上一次已知值
```

实测「无数字」共 12 段，其中 6 段与按钮暗态重合。**暗态 ≠ 暂停**（33.2s 是暗态 + ❚❚ + 正在跑）。

## 6. 状态机与逐帧计数伪代码

**一条铁律：全局帧数只由费用条的像素决定。** 倍速键、暂停键只用来回答「什么时候可以不看条」。

```
每帧:
    row      = 费用条 ROI 逐列中位数
    fill     = 左端起连续 >=240 的像素数          # 0..bar_w
    grey146  = count(|row-146| <= 10)
    grey88   = count(|row- 88| <= 8)
    state    = MAX / MAX_FADE / TRACK / EMPTY

    # 暂停键：形状占比带滞回（>=0.20 运行中、<=0.11 已暂停、中间沿用上一拍，见第 5 节）
    running  = ...

    if 不在关卡里（一段时间没再见过费用条）:
        delta = 0                                  # 关卡外一帧都不记
    elif state in (MAX, MAX_FADE):                 # 满费：条被画出来 = 一定在关卡里
        if not running:            delta = 0       # 暂停
        elif 倍速键上没数字:        delta = 0       # 冻结，绝不猜一个倍速
        else:                      delta = 30 * m * dt
    elif state == EMPTY and 上一拍相位 <= 0.75:
        delta = 0                                  # 条这一拍压根没画出来：冻结
    else:
        delta = 相位重同步(fill)                    # 像素通道：整数逻辑帧，与倍速无关
        # 走这一支的空条 = 刚回费（上一拍相位贴在 1.0 上），记的是「新一费的第 1 帧」
```

三条路子：

- **像素通道**：条画着填充（含一费开头那两帧的 0 宽平段、以及回费后条收起的那一帧）
  → 数出条走出来的整数逻辑帧。
  **和倍速完全无关**：1X / 2X / 0.2X / 子弹时间都不用读倍速，`_resync` 自己会挑出前进帧数
  （因为一费恒为 30 逻辑帧，倍速只改变每秒有多少逻辑帧，不改变条本身一格走多少像素）。
- **满费挂钟通道**：**只在 MAX / MAX_FADE**。相位被游戏钉在 0，像素里没有任何时间信息，
  速率有两个来源，**顺序不能换**（子弹时间下倍速键上是没有数字的）：
    1. 子弹时间 `>>>`   -> **固定 6 帧/秒**（= 30/5），与倍速设置无关（见 3.1）
    2. 倍速键上的数字   -> `30 × m`（1X 给 30 帧/秒、2X 给 60 帧/秒）
  两个都读不到（按钮淡出 / 被部署遮罩糊掉）就**冻结**，不猜 ——
  「没数字」只能推出「不知道倍速」，推不出「0.2 倍速」（暂停菜单里也只剩三条箭头）。

  代价：满费 + 按钮糊掉那段会冻结、少记几帧到几十帧。这是**故意**的：
  猜 1 倍速和猜 0.2 倍速各错 5 倍，比「冻结」错得离谱。
- **冻结**：以上都不成立 → `delta = 0`。

必须接受的事实：**条冻住的那段时间，像素里不存在任何时间信息**，满费段只能给到挂钟估算精度。
这条通道**带小数**：不足 1 个逻辑帧的余量会跨暂停接着攒（`Counter._clock_frac`），
`FrameResult.elapsed_f` 就是「整数帧 + 余量」，面板在满费时印两位小数。
实测 `Desktop 2026.10.05 - 21.43.13.03`（子弹时间那段，真值 33.79 帧）：整数部分 33、
余量 +0.79 —— 小数位把「挂钟估算的零点几帧」如实露出来了，而不是每拍取整丢掉。

### 为什么「条不可读就按 1 秒 30 帧涨」是错的

1. **`EMPTY` 不能算「在关卡里」**：主菜单 / 仓库 / 编队 / 关掉结算 / 切场景读出来全是 EMPTY，
   关卡内的「0 费」也是 EMPTY，像素上完全一样。旧逻辑在这些帧上走挂钟通道，
   于是「不在关卡里也在一秒 30 帧地涨」。
   实测：一段 4 秒的「1-7 关卡选择」录屏凭空记了 217 帧；本机 obs 录像里
   空条帧也被凭空记了 15 帧。现在 EMPTY 只能走像素通道（相位对不上就冻结）。
2. **挂钟通道必须乘倍速，而倍速来自倍速键**：倍速读错一倍，整段就错一倍。
   实测「一费 30 帧」被算成 **62 帧**，就是旧版在倍速读不出来时默认 2X 造成的。
   现在读不出来就冻结 —— 宁可少记，不要凭空多记。

### 怎么验证「一费 = 30 帧」

- `tools/check_speed_mix.py`：把 1X / 2X / 0.2X / 暂停 / 满费 / 关卡外混在一起喂给状态机，
  和**算出来的精确真值**比总帧数（现在 9 个场景全部 ±1 帧以内）。
- `tools/check_bar_linearity.py`：不需要知道倍速，直接卡「这一段记的帧数」和
  「费用条自己走了多少像素」是否对得上 —— 记多了、记少了都会被抓出来。
- `run_reader.py` 跑完打印的「**费用周期**」：条回卷一次实际记了多少帧，
  正确时应恒为 30（详见第 13 节）。
- `tools/check_state_synth.py` 的第二段：用数学精确的合成条跑 99 个周期，
  直接打印逐周期长度，应当全是 30、偶尔 31。
- `tools/check_state_synth.py` 的第三 / 第四段：帧操逐帧精度（每一拍当场 +1，
  含回费归零那一拍）、暂停期间条读不出来时不许补帧（见第 13 节）。
- `run_reader.py` 打印的「实测帧率」只能当粗估（分母要乘倍速读数、样本又短），
  不要拿它下结论 —— 见第 13 节。

## 7. 已知坑（本机实测踩到的）

1. 满费判据用 `fill == 满格` 会漏判（见第 1 节）。
2. 满费退出有 14 帧 88 灰态，会被误读成相位 0。
3. MAX 标签会超时消失，出现「EMPTY 但 DP 仍是 99」的形态。
4. MAX 期间相位钉在 0，退出后从 0 重锚，不要做相位穿越。
5. 暂停/倍速按钮有亮/暗两种渲染，亮度阈值法失效，必须用形状特征。
6. 子弹时间 >>> 不显示倍速数字，但**速率是确定的 6 帧/秒**（与倍速设置无关，见 3.1）——
   别用缓存的倍速去除以 5。「沿用上一次倍速」只在按钮淡出糊掉时才用。
7. ffmpeg 的 crop 会静默 clamp：`x + w > 帧宽` 时自动左移 x（本次把 2200 改成了 2160），
   导致两次裁剪对不上、白条起点差 40px，排查了很久。**ROI 不要越界，并断言裁剪参数。**
8. ROI 必须按窗口尺寸实时计算（用户会改窗口大小/位置），条槽右端锚定窗口右边缘：
   2560 宽时 = 240px、1920 宽时 = 180px，即 `bar_w = round(180 * W/1920)`（宽高比 > 16:9 时用 H/1080）。
9. **满费期间相位被钉在 0，退出后条从 0 重新涨** —— 所以满费段不要去「推进累加器」，
   冻结相位、等条回来时用相位重同步重新对上就行（上一拍相位 > 0.75 时允许跨回费边界）。
10. **HDR / PQ 采集**：UI 白从 255 掉到 ~122，所有绝对亮度阈值都失效。
   费用条走 features 的「亮度自适应」还原（第 10 节）；
   倍速键的箭头判据也从「绝对 ≥200」改成「本帧白电平的相对阈值」——
   绝对阈值在 HDR 录像上命中率是 0.0000，子弹时间永远认不出来。
11. **倍速键上没数字不等于 0.2 倍速**：暂停菜单里也只剩三条箭头（实测 23.53 录像全程如此）。
   「没数字」只能推出「这一刻不知道倍速」，不能据此把速率除以 5 ——
   5 倍的系统偏差比不计数严重得多。
   要认子弹时间必须用**正的**判据：中部箭头带相对本帧白电平而锐利发亮（见第 10 条）。
   认出来了就按**固定 6 帧/秒**算（见 3.1），不是「当前倍速 ÷ 5」。

## 8. 暂停键图标会「闪」——「连续 5 拍确认门」已经删掉（2026-10-06 反转）

**现象（实测）**：游戏暂停时，右上角的「继续」按钮（▶）会以 **2~3 个渲染帧**为单位闪回
「运行中」的双竖条形状。一段 76 秒的全程暂停录像里闪了 28 次；逐帧核对过：静止时形状占比
0.062，闪的那两帧是 0.2378 —— 和真的在跑时一模一样，用阈值分不开。

**当时的对策**：满费挂钟通道加一道门 —— 刚从暂停回来时，「运行中」必须连续保持 5 拍才允许
补帧（`CLOCK_ARM_FRAMES`）；确认之前那几拍的挂钟时间先攒进 `clock_wait`，确认的一刻一次性
回填（所以当时那版「运行中满费 180 帧」仍然一帧不丢）。

**为什么反转**：那道门把**真实的帧操**一起吃了。满费 + 子弹时间（恒 6 帧/秒）下玩家的
一次帧操是「暂停 → 跑 17~67ms → 再暂停」，在 60fps 录像里是 1~4 拍，一律短于 5 拍门限，
于是**每一下操作都记 0 帧**（用户原话「操作太快记不了」）。

实测 `Desktop 2026.10.06 - 18.32.40.02`（24.1 秒 / 1448 拍，全程满费，就是用户的帧操录像）：

| | 累计逻辑帧 |
| --- | --- |
| 旧（5 拍确认门） | **21** |
| 新（读数说在跑就记） | **41**（外加余量 0.41 帧） |

逐拍核对：29 段「运行中」里 20 段只有 1~3 拍；前 16 段（2.38s~9.39s）倍速键上还画着
数字（1X，每拍 0.5 逻辑帧），从 11.25s 起键上只剩三条箭头（子弹时间，每拍 0.1 逻辑帧）——
41 帧和「逐段 拍数 x 速率」累加的结果对得上。

**那段录像里根本没有「闪」**：连续暂停 4.3 秒一次都没闪。为了不再靠图标形状下结论，这次拿
**暂停遮罩的整屏变暗**做了交叉验证：取战场上一块 800x380 的区域算平均亮度，暂停时 35、
运行时 70，两者完全不重叠；那段录像里 262 拍「运行中」的读数**全部**落在亮的一侧 ——
它们全都是真的在跑，不是闪烁。这条「整屏变暗」的判据比图标形状可靠得多，留作后备。

**现在的规则**（`state.py` 的 `Counter._clock`）：`CLOCK_ARM_FRAMES` / `_need_confirm` /
`_clock_wait` 三个东西连同 `clock-wait` 这个通道名一起删掉。这一拍读数说在跑，就按
`rate * dt` 记；不足 1 个逻辑帧的余量留在 `_clock_frac` 里**跨暂停、跨通道**接着攒
（帧操一下只跑 0.3 帧，十下就是 3 帧）。只有 `resync()`（画面整段读不到）才允许丢掉余量。
面板在满费时印 `elapsed_f`（两位小数），就是「整数帧 + 这个余量」。

**万一「闪」回来了怎么认**：表现是「暂停着数字还在一格一格挪」。`18.32` 那段录像里
连续暂停 4.3 秒数字一动不动，那才是正确的样子。真回来了就上「整屏变暗」那条判据，
**别退回拍数门限** —— 拍数门限在实时链路（894Hz 采样，5 拍只有 6ms）本来也拦不住 33ms 的闪。

**验收**：

1. `tools/check_state_synth.py` 的 `fast_frame_step_at_max`：满费下「暂停 30 拍 → 只跑 2 拍」
   重复 12 轮，在 1X / 2X / 子弹时间三种速率下，累计帧数必须和真值**逐位相等**
   （旧逻辑每轮丢 1 帧 / 1 帧 / 0.2 帧）。
2. `tools/check_speed_mix.py` 的「暂停 60 秒 → 0 帧」「关卡外 10 秒 → 0 帧」仍然通过。
3. 对照录像 `2026-10-04 19-08-39.mp4` 仍是 **390 帧**（那条通道没用到挂钟，逐项不变）。

## 9. 关卡判定：只有「费用条被画出来」才算在关卡里

**现象（录屏实测）**：PC 窗口模式录整个桌面时，主菜单 / 仓库 / 编队 / **关卡选择界面**里
费用条根本不在画面上，读出来是 `EMPTY`。旧逻辑在 `EMPTY` 帧上照走像素 / 挂钟通道，
于是一段 4 秒的「1-7 关卡选择」录屏里凭空记了 **217 帧**（≈7.2 秒游戏时间）。

**规则**（`state.py`）：只有下面三种状态算「费用条被画出来了」：

| 状态 | 含义 | 算不算在关卡里的证据 |
| --- | --- | --- |
| TRACK | 条在推进 | 算 |
| MAX | 满费（整条灰底 + MAX 字样）| 算 |
| MAX_FADE | 满费退出的过渡（88 灰）| 算 |
| EMPTY | 条槽里没有填充 | **不算** |

`EMPTY` 必须不算：关卡内「0 费」和关卡外「根本没有条」在像素上完全一样。
连续 `BATTLE_HOLD_FRAMES = 120` 帧（1~2 秒 @60Hz）没见过费用条就判「不在关卡里」：
`delta = 0`，并且 `resync()` 重新锚定，这样下一局开局不会把上一局的余量接上去。
120 帧的滞回是用来兜住关卡内的短暂读不到（切场景、被部署动画挡住）。

同一段录屏：改前 217 帧 → 改后 **0 帧**。

但「条被画出来」只是**必要**条件之一，不是充分的：菜单 / 仓库 / 切场景时条 ROI 会压到
别的高亮 UI 上，读出一条**宽度恒定的假白条**（状态是 TRACK，和真条一模一样）。
另一半判据（游戏 HUD 画没画出来）见第 23 节。

## 10. HDR / PQ 采集：白电平从 255 掉到 122

**实测（两段 NVIDIA 录屏，`hevc Main 10, yuv420p10le, smpte2084`）**：

| 画面元素 | SDR 录像 | HDR 录像 |
| --- | --- | --- |
| 填充白 | 255 | **122** |
| 轨道灰 | 55..68 | 51..58 |
| 满费灰底（对应 146）| 146 | **94** |
| 满费退出过渡（对应 88）| 88 | ~70 |

暂停键 / 倍速键不受影响（它们本来就用相对阈值）；费用条的判据全是绝对阈值
（250 / 146 / 88），于是 HDR 下永远 `EMPTY` → 状态机退回挂钟通道 →
画面上的表现就是「不看条了，按 1 秒 30 帧瞎涨」。而且 94 正好落进「88±10」区间，
真正的满费会被读成 `MAX_FADE`。

**规则**（`features.py`）。先判断这一行是不是「整体被压暗」（`_dim_anchor`，白电平取 99 分位）：

| 行内白电平 | 判断 | 处理 |
| --- | --- | --- |
| < 100 | 关卡外的暗场景（实测整行 9..24），不是 HUD | 不还原 |
| 100 .. 149 | HDR 那种被压暗的 HUD | 还原 |
| >= 150 | SDR 的另一种渲染（蒙遮罩的半透明白 151..165、满费退出时刻的亮字 154）| 不还原 |

要还原时分两路走，只用一种一定有一头是错的：

| 判据 | 怎么还原 | 为什么 |
| --- | --- | --- |
| 填充（白）| 按白电平等比抬亮 `x * 255 / hi` | 填充就在白电平附近；等比抬亮后阈值等价于 0.965 x 白，边界最稳 |
| 灰底（146 / 88）| PQ 反变换到亮度 → 除以白电平 → sRGB（`restore_pq_row`）| 灰底在中间灰度：等比抬亮会把 94 抬成 197，两个灰底判据都命中不了；PQ 反变换把 94 还原成 ~146、70 还原成 ~88 |

白电平是**逐帧测**的，所以换 HDR 亮度档 / 换 SDR 白电平都不用改常数；SDR 画面白电平 = 255，
判据自动退化成恒等变换，已标定过的画面逐像素和以前一样（`docs/v2_frames.csv` 逐帧对齐 0 差异）。

**验收**：

| 录像 | 改前 | 改后 |
| --- | --- | --- |
| 17.08（SDR 实战，3401 帧）| 2142 逻辑帧 | **2142 逻辑帧**，和参考表逐帧一致 |
| 10-04 00.37（HDR 实战，2393 帧）| 条读不出来，51 帧全靠挂钟 | **51 帧**，像素通道 1430 帧 |
| 10-03 23.53（HDR 满费 + 暂停，1895 帧）| 满费被读成 MAX_FADE | **MAX 1894 帧** |
| 15.31 关卡选择界面（录桌面，238 帧）| 217 帧 | **0 帧** |

## 11. 录整个桌面时 ROI 要平移：--client / --roi-offset

NVIDIA 录屏录的是整个桌面（2560x1600，含标题栏和任务栏），而游戏客户区是
2558x1440、原点在 `(16, 45)`。ROI 是按「客户区尺寸 + 客户区原点」定的，所以抽流时要交给读取器：

    python run_reader.py "<录像.mp4>" --client 2558x1440 --roi-offset 16,45

不写这两个参数，ROI 会按 2560x1600 算、整体偏掉（垂直差 45px，读到的全是背景）。
`geometry.reframe_layout()` 把三个 ROI 整体平移再按画面尺寸裁掉越界部分 ——
录桌面时右边缘会被裁掉约 14px，条可见宽 226px（真实 239.81px），
计数器用 `Counter(visible_w=...)` 按真实宽度算、画出来才截到可见段。

**抽流缓存目录名会把这三项编进去**（`cache_suffix()`）：`_barbox` / `_c2558x1440` /
`_om2_45`（负号写成 `m`）。必须这样，因为缓存里存的就是按那组 ROI 裁出来的灰度流 ——
同一段录像换一组 ROI 就是另一套数据。以前只区分了手工条框，于是「先带
`--roi-offset` 跑一遍、再不带跑一遍」会命中上一次的缓存，读的是上一次的位置：
画面里明明没有费用条，程序却一本正经地报数（实测两个 2558x1440 的录像换了 offset，
读数全废）。

## 12. 测试用：手动「暂停计数」开关

前端的「暂停计数 (P)」是人工开关，和游戏自己的暂停无关：
按下去以后数字**一动不动**（读数、预览照常刷新），方便对着录像 / 轴逐段核对。
放开时不是把按住的那段补回来，而是 `resync(keep_battle=True)` 重新起锚：
按住的一段既不会事后计入、数字也不会跳。为什么不补：按住期间游戏可能经历
暂停 / 满费 / 切出屏幕，算不出一个可靠的正确值，猜一个反而比不记更差。
`tools/check_speed_mix.py` 里的「手动暂停计数」用例就是钉这两件事的。

## 13. 一费到底几帧：看「费用周期」，不要看「实测帧率」

「一费 = 30 帧」唯一靠谱的口径是**条回卷一次记了多少帧**，`run_reader.py` 现在直接打印：

    费用周期  : 一费 30 帧（中位）  <- 99 个完整周期，范围 30..31 帧

它不用任何帧率、也不用倍速读数 —— 只数「条从空走到下一次空」。偶尔冒出 31 是正常的：
定点累加器每逻辑帧加 `SCALE//30`，攒下的截断误差每 11 个周期满一次 EPSILON，
第 11 费就会多花一帧（见 `fp24.py`），`tools/check_state_synth.py` 把这条也当成了回归项。

**为什么不能拿「实测帧率」下结论**：那个数是「像素通道累计逻辑帧 / 累计等效挂钟秒数」，
分母要乘倍速读数，样本还常常只有十几帧。实测一段 14 秒录像它给出 27.857 fps，
但同一段录像里条一步不差地走完了一整费 —— 差异全来自抽样边界（第一拍 delta=0、
样本起点正好落在平段上），不是计数错了。它现在只作粗估保留。

### 回费那一帧条是「画满」的，下一帧才归零

这是本轮修掉的关键 bug，也是「一秒的总数对、一秒之内全错」的根源。

实测一段 60fps 1 倍速录像，回卷处的可见宽度序列是：

    223, 232, 240, 0, 0, 6, 15, 23, 31, 40, ...

也就是说：条在累加器刚好攒满的那一帧**画满（240 = 相位 1.0）**，**下一帧**才归零。
一费 30 帧里宽度非零的只有 29 帧，`0` 只出现在归零后的第 1 帧（第 2 帧就变 6 了）。

早先 `fp24.CostTiming.phase()` 把「刚回费」表示成相位 0（宽 0），等于给模型喂了
一条「回卷处有两个连续 0 宽帧、根本没有 240」的信号。后果：**每一费的回费帧都
匹配不上、被判 bar-reject**，一费之内必然差 1 帧。现在 `phase()` 在
`frames_since_cycle_start == 0` 时返回 1.0（用 `cycles > 0` 排除「还没起锚」）。

同样的错误也出现在两个自检脚本的合成信号生成器里（写成 `(帧数 % 30) / 30`），
等于拿一条和游戏不一样的信号去测状态机，所以以前测不出这个问题。两处都改成按
「第 n 个逻辑帧 = 相位 n/30，n 为 30 的整数倍时取 1.0」来画。

`tools/check_state_synth.py` 的 `cycle_lengths()` 是这条的回归项：连续跑 3000 拍，
逐周期长度必须是 30，偶尔 31（见下文）。

### 归零那一帧 = 新一费的第 1 帧，必须**当场**记（帧操时最明显）

条走满之后，游戏会把条收起来一拍做回费动画：`... 232, 240, 0, 6, 15 ...`（实测 60fps 1X）。
那个「0」不是「条没了」，而是**新一费的第 1 帧**（相位 1/30，按 `synthesis.py`
的曲线正好画出来宽度 0）。它和关卡外的 EMPTY 在像素上都是「一个白点都没有」，
唯一的区别来自上下文：**它的上一拍相位贴在 1.0 上（条是满的）**。

老逻辑把「暂停 + 空条」一律判成不计数。帧操（暂停着一下一下推）时每一拍正好是 1 个逻辑帧，
于是回费边界那一拍不涨、下一拍一次涨 2 —— 计数器看起来「卡了一下」，实际上是把
**归零那一帧**吞了、延后 55 个视频帧（0.9 秒）才补上。打轴时这 0.9 秒就是硬伤。

现在：空条读数进像素通道的唯一入口就是「上一拍相位 > `WRAP_MIN_PREV_PHASE`(0.75)」，
走这条路的那一帧在 CSV / 面板里标成 `wrap` 通道。三条性质：

- **每跨一个回费边界最多命中一次**：回费后相位立刻掉回 1/30，第二拍就不再满足判据；
- **判据和 `_pixel` 的 `allow_wrap` 用同一个常数**，不会出现「这里认了、那里不认」的裂缝；
- 和它一起退休的是老的「`fill=0` 要连续 5 拍运行中才放行」那道门 ——
  新门更窄（要求上一拍条是满的），而且不依赖暂停键读数（帧操时暂停键本来就是「已暂停」）。

回归项：`tools/check_state_synth.py` 的 `frame_step_precision()`（暂停着逐帧推 300 拍，
每一拍都必须当场 +1，含归零那一拍）和 `pause_missing_bar()`（暂停期间条读不出来时
一帧都不许补 —— 老代码在这里凭空多记过 61 帧）。

真实录像上的效果（`2026-10-04 19-08-39.mp4`，客户区 2558x1494 @(-5,45)）：

| | 累计逻辑帧 | wrap 通道 |
|---|---|---|
| 修前 | 386 | — |
| 修后 | **388** | 13 |

多的那 2 帧用**游戏自己的费用数字**核对过，确实存在、老代码漏了：
idx 628 数字 `20 → 21`、idx 3420 数字 `28 → 29`（两处都是条走满 → 归零，
紧接着画面切走好几秒，老代码在那儿重新起锚把这帧丢了）。其余 11 次 wrap 只是
把同一帧从「晚一拍补」改成「当场记」，总数不变。

### 起锚那一拍也要补「周期开头那几帧」（费用条空 → 第一个像素）

同一类漏帧的第二种表现：**条第一次被读到的那一帧**。用户报的原话是
「费用条空（第 0 帧）到出现第一个像素（第一帧）还是不记录」。

条在周期第 1 帧画出来宽度是 0（相位 1/30），和关卡外根本没画条长得一模一样，
所以「第一次读到条」通常已经是本费的第 2 帧（实测 fill=6/7/8 -> 周期第 2 帧）
或第 3 帧（fill=15 -> 第 3 帧）。老逻辑起锚一律记 0 帧（`_start` 的注释写着
「这一步前进的帧数不计入总数」），于是那一帧被吞掉，**整段录像的帧号从此差 1**，
打轴正好差一格。

现在起锚这一拍补 `k - 1` 帧（k = 起锚落在周期的第几帧）。k 由宽度反推 ——
相位-宽度曲线单调、每帧 8.3px，所以这个位置是**被读数证明过的**，不是猜。
上限 `ANCHOR_MAX_CATCHUP = 2` 帧：

| 起锚读到的 fill | 反推 → 周期第几帧 | 这一拍记几帧 | 通道名 |
|---|---|---|---|
| 6 / 7 / 8（开战） | 2 | 1 | `anchor-head` |
| 15 | 3 | 2 | `anchor-head` |
| 129（半路重现） | 16 | 0（补不了） | `anchor` + 告警 `anchor-late` |

为什么卡上限：条如果是在别的地方（切场景 / 关菜单 / 被遮挡）半路重新出现的，
前面丢了多久**无法证明** —— 宁可少记也不猜。实测那条 1 倍速录像里 3 次是开战
起锚（k=2）、1 次是半路重现（k=16），两者分得很开。

真实录像上的效果（`2026-10-04 19-08-39.mp4`，客户区 2558x1494 @(-5,45)）：

| | 累计逻辑帧 | 费用周期 |
|---|---|---|
| 抄前人那版 | 386 | — |
| 修「归零那一帧」后 | 388 | 30 帧 × 11 周期 |
| 再修「起锚补帧」后 | **391** | 30 帧 × 11 周期（**不变**） |

补帧只改帧号的起点，不改周期长度：从起锚那一拍往前数 30 个逻辑帧，相位必然回到
同一处，所以「一费 30 帧」这条硬指标不受影响。

回归项：`tools/check_state_synth.py` 的 `anchor_head_catchup()` —— 起锚落在周期
第 2 / 3 帧要补 1 / 2 帧，落在第 4 / 16 帧一帧都不许补，且一个费用周期恒为 30 帧。

### 卡顿那一帧：上限要按「距上次采纳」算，不能按单帧间隔算

物理上限（游戏内最高 2 倍速 = 60 逻辑帧/秒，再快只能是误读）原来的分母是**单帧间隔**：
`bound = 60*dt + 3`。60fps 录像下 dt = 1/60，bound = 4。

实测踩到的坑：某一段里条读数是 `fill=23`，下一帧变成 `65` —— 游戏卡了一下，一帧里
过去了 5 个逻辑帧。`_resync` 要的就是 k=5 > 4 → 判 `pixel-jump`、整帧扔掉；扔掉以后
相位没前进，下一帧同样差 5 → 继续扔……**整个费用周期一格都记不到**，直到条回卷才
自愈。表现正是「一秒的总数对、一秒内的位置全错」（实测那段连着拒了 42 帧）。

改成分母用 `_since_accept`（距上一次**被采纳**的读数过去了多久）之后：第一帧仍然
被拒（上限没有放宽，误读照样拦得住），但被拒的这一帧把时间攒了起来，下一帧上限就
够用了，**一帧之内自愈**。连续正常采纳时 gap ≈ dt，上限和以前一样紧。

回归项：真实录像 `2026-10-04 19-08-39.mp4` 的 `pixel-jump` 从 42 降到 1，
而且那 1 次之后立刻恢复了。

### 画面被放大 / 裁剪过时用 --bar-box

实测一段 OBS 录像整个画面被放大并裁掉右上角：费用条宽 419px（正常 240px，1.75 倍）、
条身 15px 高（正常 8px）、右上角的暂停 / 倍速键完全不在画面里。这种录像算不出客户区几何，
按窗口尺寸推出来的 ROI 全是错的。这时直接给条框：

    python run_reader.py "<录像.mp4>" --bar-box 2133,1436,419,15

此时暂停 / 倍速通道自动关闭（`layout.buttons_visible=False`）：暂停读数返回「运行中」、
倍速读数返回 nan，挂钟通道按既有规则冻结。代价是满费期间真按了暂停会多记几帧，
条正常推进时不受影响。


## 14. 实时链路的两条硬指标：采样 ≥120Hz、面板刷新 ≥60Hz

这两条不是「好看」问题，是用户实测报上来的「游戏 1 倍速下像在漏帧」的全部原因。
采样这一条一开始定在 60Hz（14.1 / 14.2），后来发现 60Hz 会在「某一拍卡一下」的时候
整帧漏采，**14.4 把它提到了 120Hz**。

### 14.1 抓屏之后只对三个 ROI 转灰度，别转整块外接矩形

实时链路一次 BitBlt 抓「三个 ROI 的外接矩形」（条在右下、按钮在右上，中间一大片是空的，
480x1106 = 53 万像素），然后在内存里切三块。原来的写法是**先把整块转成灰度再切**：

| 做法 | 耗时（本机 2560x1600，实测 300 次平均） |
|---|---|
| `to_gray(整块 480x1106)` | **7.33 ms** |
| `to_gray(三个 ROI)` = 240x17 + 200x160 + 200x160 | **0.73 ms** |

差 6.6 ms。三个特征加起来才 1.2 ms，抓屏 8.9 ms —— 也就是说这一行占了**采样周期的
三分之一**：不省的话一拍 18.3 ms = 54.6 Hz，省完一拍 ≈11 ms，配速跑到 60 Hz（`--rate 60`）
才有余量（`--rate 0` 能跑到 ~90 Hz）。两种做法逐像素完全相等，改的是常识不是算法。
（这段是 60Hz 时代的结论；14.4 把默认采样率提到 120Hz 之后，抓屏这一步仍然是全过程
最贵的一步，见 14.4 的实测表。）

为什么 1 倍速下对采样率最敏感：1 倍速时每拍只前进 **0.5 个逻辑帧**，
条每拍只动 4px —— 判据余量本来就比 2 倍速小一半。采样慢到接近 33ms（游戏一个
逻辑帧的显示时长）就更没有余量了。用户要求过「识别 16ms 的精度」，16ms 就是 60Hz。

### 14.2 面板重绘要 ≤15ms —— 16 是个**坏数字**（Windows 定时器粒度 15.6ms）

`ui.py` 的 `poll_ms` 原来是 **60**（16.7 Hz），而 1 倍速下游戏每秒走 30 个逻辑帧。
结果是面板上的数字每次刷新跳 **2 帧** —— 用户逐帧看录像时，游戏里的条每 2 个视频帧
走一格、面板上的数字却每 3~4 个视频帧才变一次，看上去就是「计数器漏帧」。

**为什么帧操（暂停着一下一下推）看不出这个问题**：帧操时每按一次条只走 1 帧、
然后就停在那儿不动，60ms 的面板照样能把每一格都显示出来（每格显示 1 次、数值正好 +1）；
只有 1 倍速连续推进时，游戏 1 秒走 30 帧、面板 1 秒只重画 16.7 次，必然跳帧。
用户的原话正是「一帧一帧过确实能做到一费 30 帧，但是游戏 1 倍速下就会识别漏帧」。

先改成了 `poll_ms=16`（当时按「16ms ≈ 60Hz」算的）。**这个数是错的。**
Windows 的定时器粒度是 **15.6 ms**，tkinter 的 `after(n)` 实际落在 `ceil(n / 15.6) x 15.6`
上 —— n=16 只比 15.6 大一丁点，于是被抬到 **31.2 ms**：实测面板只有 **32.8 Hz**，
刚好压在 33.3 ms（1 倍速下一个逻辑帧的显示时长）上，还是会偶尔跳 2 帧。

改成 `poll_ms=8` 之后实测周期 **15.55 ms（64 Hz）**，正好翻一倍。

实测口径：`--demo-axis`，真实 Tk 主循环（`mainloop`）跑 6 秒，记录每一次 `_tick` 的
挂钟间隔取中位数。一个配置一个进程，免得几次运行互相污染：

| `poll_ms` | 实测周期（中位） | 面板速率 | 备注 |
|---|---|---|---|
| 4 | 15.53 ms | 64.4 Hz | |
| **8（现用）** | **15.55 ms** | **64.3 Hz** | |
| 16（旧值） | 30.53 ms | 32.8 Hz | 跨过 15.6 就翻倍 |
| 33 | 46.65 ms | 21.4 Hz | `ceil(33/15.6)=3` 档 |

两条要点：

* **规律是「跨过 15.6 就翻倍」**，所以 `poll_ms` 千万别往回调大；4~15 之间结果一样
  （都落在 15.6 ms 那一档）。
* 上限**不是**定时器，而是**整窗口重绘约 14.7 ms**：把 `poll_ms` 降到 4 也还是 64 Hz。
  再想快就得去减重绘面积/重绘内容（见 19.1），调 n 没用。
  CPU 代价很小（poll=16 约占一个核的 5%、poll=8 约 13%）—— 那 14.7 ms 大半是在等窗口
  合成，不是在烧 CPU。

注意：这只影响**显示**，采样和计数一直在 `live.py` 的独立线程里跑，从来没停过。
面板上那栏「面板 N Hz」可以当场核对：只要明显高于 30 就不会跳帧。

### 14.3 「实测帧率」这个数天生有 ±1 帧/秒 的误差，不要拿它判漏帧

实测帧率 = 像素通道累计帧数 / 累计挂钟秒数。窗口头尾各差半帧，1 秒的窗口就是 ±3%：

| 录像 | 窗口 | 实测帧率 | 真值 |
|---|---|---|---|
| `19-08-39`（连续推进 8 秒） | 8.0 s | 29.94 | 30.0 |
| `20-02-06`（连续推进 1 秒的碎段） | 2.8 s | 29.46 | 30.0 |

所以短窗口下它会报 29.x —— 但其实一帧都没漏。**「一费几帧」才是精确口径**
（它不除时间、不乘倍速，窗口边界那点量化误差进不来）。因此 `run_reader.py` 现在：

* 走完过至少一个完整费用周期 -> 只报「费用周期 一费 N 帧（中位）」，**不报**实测帧率；
* 没走完过完整周期 -> 才拿实测帧率兜底，并且样本不足 2 秒就直接说「不报数」。

### 14.4 采样率必须 ≥120Hz：整帧漏采（混叠）与 `wrap-missed` 通道

用户的原话是「现在基本上不出错了，一费稳定 30 帧，但是**有时候第 0 帧还是不读、
第一帧补了两帧**」。这不是计数错（总数照样对），是**采样漏了一拍**。

**机理**：游戏里一个逻辑帧的内容会在屏幕上停留一个逻辑帧的时长（1 倍速 = 33.3ms）。
如果两次采样之间的间隔超过它，那一帧的内容就**从没出现在任何一个采样点上** —— 于是
计数器在下一拍一次性补 2 帧。结论很硬：

| 抓屏间隔 g | 整帧漏采的概率 | 说明 |
|---|---|---|
| g ≤ 33.3 ms | 0（不可能） | 任何 33.3ms 的窗口里至少有一个采样点 |
| g = 40 ms | ≈ 20 % | 概率 = (g − 33.3) / 33.3 |
| g = 50 ms | ≈ 50 % | |
| g ≥ 66.7 ms | 100 % | 必然吞掉整整一帧 |

所以「漏不漏」只看一件事：**单次采样间隔会不会超过 33.3ms**。提高采样率不是直接消除
漏采，而是把「基准间隔」压下去、给卡顿留出余量。

**本机实测（配速压测，同一套抓屏+特征负载，各跑 6 秒）**：

| 配速 | 实测有效速率 | 一拍耗时（中位） | 间隔中位 | 间隔 p99 | 间隔最大 | >33.3ms 次数 |
|---|---|---|---|---|---|---|
| 不限速 | 145.8 Hz | 6.52 ms | 6.86 ms | 9.29 ms | 11.75 ms | 0 |
| `--rate 150` | 139.4 Hz | 6.41 ms | 7.17 ms | 12.00 ms | 12.32 ms | 0 |
| `--rate 120`（现默认） | 109.7 Hz | 6.98 ms | 9.11 ms | 11.84 ms | 13.09 ms | 0 |
| `--rate 60`（原默认） | 59.7 Hz | 6.87 ms | 16.75 ms | 20.86 ms | 21.52 ms | 0 |

看「余量」最直观：60Hz 时间隔中位 16.75ms、离 33.3ms 的漏采线只剩 **2 倍**余量，
一拍卡 17ms 就跨过去了；120Hz 下中位 9.11ms、余量 **3.7 倍**，抗卡顿能力翻倍。
（`--rate 120` 实测只跑到 110Hz，是 sleep 配速每拍约 0.8ms 的固定开销；间隔 9.1ms
比 8.3ms 的目标略大，对结论没有影响。）代价是 CPU：一拍 ~7ms ≈ 一个核的 75%。

**为什么不能靠「多抓几次小的」再提：** GDI 的 BitBlt 每次调用有约 3.3ms 的固定开销，
面积只是次要项，所以「抓 3 块小的」比「抓 1 块大的」更慢 —— 现在的做法已经是最优解：

| 抓法 | 面积 | 中位耗时 |
|---|---|---|
| 三个 ROI 的外接矩形（现用） | 480x1106 = 53.1 万 px | **6.70 ms** |
| 按钮并集 | 480x160 = 7.7 万 px | 3.51 ms |
| 费用条 | 240x17 = 0.4 万 px | 3.32 ms |
| 按钮并集 **+** 费用条（2 次 BitBlt） | 8.1 万 px | 6.74 ms |

**新增的自查手段**（面板性能栏 / `LiveStats`）：

* `gap_ms` / `gap_max_ms`：相邻两次抓屏时间戳的间隔、最近 120 拍的最大值。面板显示
  「最大间隔 ⚠ XX.X ms（超过 YY.Y ms，可能漏采）」。**门限跟着倍速走**：一个逻辑帧的
  显示时长 = 1000 / (30 × 倍速)，1X → 33.3ms、2X → 16.7ms（写死 33.3ms 的话
  2 倍速下明明在漏采也不报警）。这是「有没有漏帧」唯一直接的证据。
* `wrap-missed` 通道：判据是「这一拍跨过了回费边界（`_crossed`），但读数**不是**空条，
  且 delta > 1」。也就是「归零那一帧没采到、下一拍一次 +2」这种情况，它会在面板上写成
  「刚回费（归零那一帧没采到，这一拍一次补 N 帧；提高采样率可消除）」，CSV 里
  `mode=wrap-missed`。和真正的 `wrap`（归零帧当场采到 → delta 正好 1）分开统计。

怎么判 `_crossed`（两条独立的证据，任一成立即可）：

* 上一拍正好停在「画满」那一帧（`cycles > 0 且 frames_since_cycle_start == 0`）——
  它的下一拍必然是新一费的第 1 帧；
* fp24 累加器自己回卷了（`timing.cycles` 涨了）。

回归项：`tools/check_state_synth.py` 的 `wrap_frame_sampled_or_missed()` —— 采到
（`240 → 0(wrap,+1) → 6(pixel,+1)`）和漏采（`240 → 6(wrap-missed,+2)`）两条路
必须分得开，且总数一致。

### 14.5 相位模型连续对不上就重锚（`phase-resync`），不要把自己锁死

这是查 14.4 时顺手挖出来的一个死角，性质比「偶尔 +2」严重得多：**相位模型会把自己
锁死，然后白丢整整一个费用周期**。

病根在 `_pixel` 的 `allow_wrap` 上：只有当「上一拍相位 > `WRAP_MIN_PREV_PHASE`(0.75)」
时才允许跨回费边界（这道门是防「暂停时闪一下 fill=0 就绕一整圈」的）。如果某一拍
漏采得太狠（缺口盖过 1/4 个周期 = 7.5 个逻辑帧，1X 下 250ms、2X 下 125ms），接下来
就是：**相位模型还停在旧周期末尾，画面已经进到新周期开头** → 每一拍匹配失败（都判
`bar-reject`）→ 相位再也不前进 → 一直要等到「新周期的某个宽度偶然撞上卡住的旧宽度」
才自愈。实测这一等就是**整整一个费用周期（30 帧）**。

修法（`REJECT_RESYNC_SECONDS = 0.2`）：相位模型连续 0.2 秒匹配不上，就认定**模型本身
已经不可信**，按当前画面重新起锚，这一拍 `delta = 0`（丢掉的帧无法证明，宁可少记也不猜），
面板显示「相位重锚（采样卡顿太久、模型对不上：这段不补帧）」、CSV 里 `warn=phase-resync`。

阈值 0.2 秒的依据：10 段实测录像共 2.7 万拍，「条还画着、只是相位对不上」的连续拒帧
最长是 **0 拍**。屏幕上确实出现过 119 连拒，但那全是 EMPTY（切场景 / 不在关卡里），
走的是关卡判定那条路，它另有关卡滞回兜底（见第 9 节），不经过这里。所以 0.2 秒既
足够快地解开死锁，又不可能误伤正常推进。

回归项：`tools/check_state_synth.py` 的 `stale_phase_reanchor()` —— 要求三条同时成立：
① 会自愈（约 0.2 秒内重锚，重锚后一拍就恢复 +1）；② 自愈之前**一帧都不许凭空虚补**；
③ 连续正常推进时一次都不能触发（每次误触发都要丢一段帧）。

## 15. 减费环境：一费 60 / 120 帧（回费速度 -50% / -75%）

### 15.1 结论先行

**回费速度 tag 改的是「一费要攒多少」，不是「每帧攒多快」。**

这一点照抄前人 `ArknightsCostBarRuler` 的 fp24：它把战斗开始时就已经定下来的修正
（突袭 / 磨难 / 合约词条 / 关卡描述红字）算作 `required`（回一费的目标量，普通关卡
= 1.0），把战斗中才生效的（负费、可露希尔、忍冬）算作 `speed`（每逻辑帧的增量）。

两种写法「一费几帧」都对得上，但**边界周期**（第几个费用周期多 1 帧）不一样，只有
按 `required` 算才和前人黑盒表对得上：

| 回费速率 | 一费逻辑帧 | 逐周期长度 | 第一次多 1 帧 |
|---|---|---|---|
| 100%（普通） | 30 | `30*10, 31, 30, ...` | 第 11 个周期 |
| -50% | 60 | `60*5, 61, 60, ...` | 第 6 个周期 |
| 1.3 秒档（沙盘 15-17） | 39 | `39*8, 40, ...` | 第 9 个周期 |
| 1.5 秒档（磨难 10-4） | 45 | `45*6, 46, 45, ...` | 第 7 个周期 |
| -75% | 120 | `120*2, 121, ...` | 第 3 个周期 |

实现就是 `fp24.required_from_frames(n) = round(n / 30 * SCALE)`，`speed` 永远是
`SCALE // 30`（逻辑帧率恒为 30，和倍速无关，也和回费速度无关）。回归项：
`tools/check_cost_rate.py` 的 `boundary_cycle_table()` 拿 fp24 跑 16 个周期，
逐项对齐上表。（39 那档文档自己写了「实际边界帧数仅能锁定在 [312, 315]」，
fp24 精确解给的是第 8 个周期，差一个位次，自检里给它留了 ±1 的容差。）

### 15.2 一费几帧由玩家手填（默认 30），自动识别只是可选功能

档位不是在战场上「认」出来的，而是在设置里**填**出来的：默认 30（1 秒 1 费），点了
「回费速度 -50% / -75%」的 tag 就填 60 / 120。

* 界面（`run_monitor.py` 开的那个面板）：「回费速率」那一行 —— 下拉档位（30 / 39 /
  45 / 60 / 90 / 120）、自定义输入框、「应用」、以及一个「自动识别（可选）」按钮。
* 设置文件 `cost_rate.json`：`{"frames_per_cost": 60.0}`。界面里改档会立刻写回这个
  文件，下次启动自动带上；文件读不动 / 内容坏掉一律退回 30（见 `settings.py`）。
* 命令行：`--settings <文件>` 指定设置文件，`--cost-rate N` 临时覆盖。

**为什么默认不自动认**：认错档比不认更糟。差一档会让绝对帧号整段漂移（30 → 60 就是
几百帧），而打轴器要的正是绝对帧号；自动识别还得等一个完整费用周期走完才敢下结论。
手填一次是确定性操作，填错了改回来立刻生效，已经数出来的像素帧会按新旧速率比例换算
（见 15.7），绝对帧号不会从头偏。

自动识别的实现仍然保留（`src/akframe/cost_rate.py`、`--cost-rate auto`、界面上的
「自动识别」按钮），当测量工具用：想知道一段录像到底是一费几帧时，它仍然是最省事的
办法（15.5 那张实测表就是它跑出来的）；分辨不清时一律报 unknown，不硬落档（15.6）。

### 15.3 不识别会怎样：整段录像是「按半速数」还是「按双倍数」

状态机把「条走多少像素」翻译成「过去了几个逻辑帧」，靠的是 fp24 的相位模型。
模型里的每逻辑帧增量是 `synthesized_width` 曲线在 `1/n` 处的宽度差：

* 一条 60 帧/费的条，如果按 30 帧/费（`required = 1.0`）去解释，模型以为每帧该涨
  8.3px，实际只涨 4.15px → 重同步只能「两帧并一帧地凑」→ **一费被数成 15 帧**，
  整段录像的绝对帧号直接减半。
* 反过来按 120 解释 60 会翻倍。

所以「一费几帧」必须先认准。打轴器要的是绝对帧号，差一档就是几百帧的系统性漂移。

### 15.4 怎么认：数「一个完整周期里条出现过多少种宽度」

这是唯一既不依赖几何常数、也不依赖挂钟的观测量：

* 条的宽度是相位的单调函数，一费 n 帧就意味着一个周期里条最多画出 n 种不同宽度
  （取整会让少数相邻帧撞成同一个值，所以实际是 n 减去几次撞车）。
* 挂钟不能用来量它：录制软件的帧率不可信（实测某录像快了 4.17%），而且玩家可能像
  本项目的测试录像那样**暂停着逐帧推进** —— 那时挂钟和逻辑帧毫无关系，只有「条出现
  过几种宽度」还有意义。

流程（`src/akframe/cost_rate.py`）：

1. **切周期**：条宽从峰值掉下来一大截（`max(6px, 30% 峰值)`）就是回费了；条整个不画
   了（EMPTY / 满费换灰底）也算收工，但只在「刚爬得很高」时才收，免得把关卡外那一长串
   空档也算成周期。
2. **取单调台阶**：段内取运行最大值 —— 真实的条单调，向下的凹口（±1px 抖动、偶发读空）
   一律当噪声。
3. **去碎步**（`_denoise_stair`）：算出台阶相邻宽度差的中位数当「典型步长」，把小于它
   40% 的小台阶并进前一个宽度 —— 那些是渲染过渡，不是逻辑帧。
4. **反推**：拿台阶的「宽度种类数」`L`（多周期取中位数）去比对每个候选档位在模型下
   的应有种类数，先得到连续估计 `raw`，再落到最近档位。

第 3 步是本轮踩出来的：一开始按「停留时间太短就丢掉」（run 长度小于 3 拍）过滤，
逐帧推进的录像好用，**正常 1 倍速播放的录像会被误伤** —— 那时每个逻辑帧只被采到
1~2 拍，和过渡碎步一样长，一周期从 29 种掉到 23 种。按步长过滤和采样方式无关。

### 15.6 认不出来就诚实说不认

* `50 / 75 / 100 帧/费` 这类游戏里不存在的档位：一律报 `unknown`，**不硬落档**。
  错落一档会让绝对帧号整段漂移，比不认更糟。
* 容差 `max(3, 4%×档位)`：观测种类数只会被两件事带偏 —— 漏采（少几种）和 ±1px 抖动
  （多几种）。实测逐帧推进的录像偏差 ±2 种，采样更稀时能到 ±4 种。再放宽就会把
  45 认成 50。
* 只有 `high` 才自动改状态机的 `required`（实时链路里换成 `low` 就只是显示，不动模型）。

### 15.7 三种改档入口

```

python run_monitor.py --cost-rate 60      实时，临时覆盖（不写设置文件）
python run_reader.py <视频> --cost-rate 60   离线分析录像
```

档位取值就是「一费几个逻辑帧」，和倍速无关（倍速只改变每秒走多少逻辑帧，不改变一费

绝对帧号不会从头就偏；挂钟通道那部分不换算（它数的本来就是真实逻辑帧）。

## 17. 换分辨率：怎么量出条槽的真实几何（实测校准表）

### 17.1 结论先行

* **尺寸**规则是对的：条槽宽 = 180 x ui_scale，而 ui_scale = min(w/1920, h/1080)；
  16:9 / 16:10 上按它推出来的条槽宽和实测差不到 1%（2558x1494 上实测 239.0 / 预测 239.8）。
* 真正会错的是**位置**：2560x1600 这一档上，预测的条槽左边缘比真实位置**右移 9px**
  （真实条槽 x2314..2552，预测 x2323..2562）。9px 约等于 1.1 个逻辑帧的填充量，
  正是「条空（第 0 帧）到出现第一个像素（第 1 帧）记不到」的一个来源。
* 所以校准只做两件事：量准条槽的**左右边缘**（-> scale + 右边缘距）和**竖直中心**
  （-> 距底），写进 `src/akframe/resolutions_measured.json`，`layout_for()` 优先读它。

### 17.2 判据：白块并集（不要用覆盖率外推）

费用「填充白块」永远从条槽左边缘开始长、最多铺满整格（1X / 2X / 子弹时间都一样），
所以把所有帧里的白块**并起来**：最左列 = 条槽左边缘，最右列 = 条槽右边缘。

为什么不用「每一列被填充覆盖的时间比例」再线性外推（v1 的做法）：那条曲线实测**不是
直线** —— d=0..50 是 1.0 的平台，60..130 掉到 0.7，d=140 处一个台阶掉到 0.3，之后才
缓慢趋 0。外推会把零点推到条槽外面很远：同一段录像 v1 量出 **376px / 478px**，
而白块并集量出来是 **239px**。并集不需要任何模型。

探针框也要**左右留余量**：白块很可能长在预测 ROI 的左边缘之外（就是上面那 9px），
探针裁在预测位置上会把白块左端切掉，量出来的宽度只会偏短，甚至因为左端不一致而完全
量不出（实测把 239px 的条量成 230px）。

### 17.3 实测数据（2026-10-04 19-08-39.mp4，客户区 2558x1494，原点 5,45）

| 量 | 实测 | 预测 | 差 |
|---|---|---|---|
| 条槽宽度 | 239.0 px | 239.8 px | -1 px |
| 条左边缘 | 2309（客户区） | 2318 | -9 px |
| 条槽中心 | 354.5（距底） | 357.0 | -2 px |

直接证据：满填充那一帧的白像素是 `x2314..2552`（连续 239 列、无空隙），同一行在空帧
是 47~68 的暗轨道。

换成实测表之后同一段录像：`bar-reject` 117 -> 51、走 `pixel` 通道的帧 2416 -> 2691、
11 个完整周期仍然全是 30 帧 —— 读得更准，不是更松。

### 17.4 怎么用

```
python tools/calibrate.py "录像.mp4" --client 2558x1494 --roi-offset=5,45          # 只量，不写
python tools/calibrate.py "录像.mp4" --client 2558x1494 --roi-offset=5,45 --write  # 量完写表 + 自动验收
python tools/calibrate.py --list                                                   # 看表里有什么
```

* 录像 10~20 秒就够，条要**正常回费**（每周期白块都会铺满整格所以不用帧操）；
  别切菜单、别叠直播弹幕 / 低三分之一字幕条之类的覆盖层 —— 盖住条就量不出，
  工具会直接报「没量出来」，**不会瞎猜一个数**。
* 表按客户区尺寸做 key，但**同一档 scale** 的尺寸也会命中（`geometry.measured_for`）：
  2558x1440 / 2558x1494 / 2560x1600 / 3440x1440 的 ui_scale 都是 1.3323，
  量其中一个够用全部。1920x1080（1.0）、3840x2160（2.0）是另一档，不会误命中。
* 走 `--roi-offset auto` 时客户区原点是拟合出来的，那种情况**只写 scale**，锚点不写
  （写进去等于把预测抄一遍当实测）。

## 18. 打包成 exe（build_app.ps1）

* 实时链路走 Windows BitBlt 抓屏（`win32.py`），**不需要 ffmpeg**；只有离线读录像
  （`run_reader.py`）才需要。所以打出来的图形程序没有外部依赖，双击就能用。
* 用 **onedir** 而不是 onefile：onefile 每次启动都要先把自己解压一遍（慢、容易被杀软
  拦、出问题没法查）；这个程序是长时间挂着的，启动快更重要。分发时把整个目录压成 zip。
* `src/akframe/paths.py` 负责「程序自己的文件放哪儿」。打包后 `__file__` 指向
  PyInstaller 的解包目录（每次启动都可能换），所以 templates/、cost_rate.json、
  layout_calib.json 一律按 **exe 所在目录** 找；开发时就是仓库根目录，行为不变。
* 用法：`powershell -ExecutionPolicy Bypass -File build_app.ps1`
  产物：`dist\ArknightsFrameCounter\ArknightsFrameCounter.exe`
* exe 是 `console=False`（不弹黑窗），所以启动就崩的话界面上看不到报错；
  那种时候用源码跑 `python run_monitor.py --no-ui` 看报错。
* `build_app.ps1` 里带中文，文件必须存成 **带 BOM 的 UTF-8**：Windows PowerShell 5.1
  读没有 BOM 的 .ps1 会按 ANSI 解，中文全乱码、字符串都被截断。
* 运行期依赖是 **numpy + pillow**：pillow 是界面画 ROI 预览用的（`ui.py` 里的
  `PIL.Image` / `ImageTk`）。漏了 pillow 打包一样能成功，但一双击就
  `ModuleNotFoundError: No module named 'PIL'` —— 实测踩过。
* 打包时**不要**去收集 `ucrtbase.dll`：它是 Win10+ 自带的系统 UCRT，本来就在
  `System32` 里、程序会直接从那加载。而且实测本机打包时，往 dist 里写这份副本会被
  安全软件拦下来（`PermissionError: ..._internal\ucrtbase.dll`，重跑和清目录都不解决，
  换个文件名写就没事 —— DLL 劫持防护的启发式误伤），`akframe.spec` 里已经把它筛掉。
* 实测校准表要**一起打进去**（`akframe.spec` 的 datas 里那两条）：漏掉的话 exe 读不到表，
  ROI 退回推算值（x2318 w240，比实测右移 9px），计数器还能用但起点那段会数不准。

## 19. 打轴器的「温度计刻度表」与演示模式（--demo-axis）

### 19.1 结论先行

* 刻度表 = 一条竖直刻度 + 一条**固定不动**的「现在」线。轴点按帧等比例摆在刻度上，
  **未来在上**，帧号往上涨时整条刻度**向下滚**，就是「现在」线在穿过轴点。
* 布局数学全部在 `scale.py` 里，是纯函数（帧号 -> 像素坐标），**不碰 tkinter**。
  所以它能脱离界面自动验证（`tools/check_scale.py`，10 组）也能离屏出图
  （`tools/preview_scale.py`）—— 界面恰恰是最难自动验证的那一层，把它剥出去很值。
* 刻度表本体是**一张 PIL 图**，贴到 Canvas 上只占**一个** item（`akframe/scale_render.py`）。
  离屏预览 `tools/preview_scale.py` 调的就是这个渲染器，所以「预览图」就是面板上真正画出来的
  东西 —— 以前 preview 自己抄了一份画法，改一边另一边不动，预览可能根本不是面板的样子。
* 为什么换成贴图：原来是 `delete('all')` + 用 Canvas 图元逐个画（刻度线/数字/标签/高亮
  约 95 个）。实测 `_draw_scale` 整体 **2.68 ms**（PIL 画 1.19 + 转 PhotoImage 0.24 +
  贴图 0.00），Python 侧开销小，Tk 要维护的 item 也从 95 个变成 1 个。
  **但别高估这一条的收益**：面板真正的上限是「整窗口重绘约 14.7 ms」（见 14.2），刻度表
  只占其中一小块。**早先注释里「95 个 item 约 1.165 ms ≈ 858 Hz」是错的** —— 那个数是
  `update_idletasks` 口径，只算了 Python 记账，没算 Tk 真正描画 + 把画面送出去。
* 一个只有 PIL 才会踩的坑：**PIL 不会自动回退字型，tkinter 会**。用 Bahnschrift（只含拉丁）
  印「现在 398.0」，Tk 上好好的，换到 PIL 就直接画成两个空豆腐块「□□ 398.0」。
  `tools/check_scale.py` 第 11 组专门防它：抓每一次 `text()` 的（字体, 字符串），
  断言汉字绝不喂给只含拉丁字母的字体。
* 刻度表**只在计数器有读数时才画**（`ui._update_prompter` 在 res 为 None 时直接 return），
  所以游戏不在关卡里时那个区域永远只有一句提示文字。为此加了 `--demo-axis`（见 19.4）。

### 19.2 公式、几何与刻度间隔

```
y(f) = pointer_y - (f - frame) * px_per_frame        # y 向下为正
```

帧号 frame 往上涨 -> 同一个 f 的 y 变大 -> 整条刻度向下滚。
`pointer_y = height * pointer_ratio`，默认高度 280、比例 0.70 -> 指针在 y=196。

默认 `ScaleGeom(width=420, height=280, ruler_w=50, px_per_frame=1.5)`：
指针往上能看 130.7 帧、往下 56 帧。缩放档 0.5 / 1 / 1.5 / 3（1 个逻辑帧画几个像素），
轴点挤在一起就调小、隔得远就调大。

小刻度的候选间隔是 (1, 2, 5, 10, 15, 30) 帧，取第一个「画出来 >= 4px」的：
1.5px/帧 时是 5 帧。大刻度固定 30 帧 —— 在明日方舟里 30 帧 = 1 费 = 1 倍速下 1 秒，
所以刻度条本身就是一把「秒表」。

### 19.3 标签防重叠与「保留带」

「现在」线上要印当前帧号，所以**指针那一行是保留带**（上下各 `label_h/2 + 5`），
轴标签谁都不许压上去。上方的轴往上排、下方的轴往下排，两侧都是
「**越靠近指针的越先占住真实位置**」，被推开的代价落在更远的那些上面 ——
因为近的那几条才是打轴时要看的。标签被推开时画一条细线连回真实刻度（`tick_y` 不动）。

「下一条」那一条轴：整行底色 + 左侧 2px 青条；另外从指针到「下一条」的刻度之间
画一根青柱（`Layout.mercury`）—— 就是温度计的水银柱，一眼看出「还差多远」。

### 19.4 演示模式（`--demo-axis`）：没有游戏画面也能看刻度表

刻度表只在有读数时才画，所以「改完刻度表到底长什么样」这件事本来只能靠玩游戏时
顺手瞄一眼。`akframe/demo.py` 的 `DemoMonitor` 把 `LiveMonitor` 的接口原样实现一遍，
只把**「画面从哪来」**换掉：按挂钟推进一个理想游戏，每走一个逻辑帧就画一根费用条。

* 条不是「直接构造读数」，而是**画成一张 ROI 图再喂给真的 `read_bar`**，
  之后交给**真的** `Counter`。所以面板上跑的是全链路
  （假画面 -> 真特征 -> 真状态机 -> 真打轴器 -> 真刻度表），只有最外面的抓屏是假的。
* 相位 -> 宽度用 `synthesis.synthesized_width`，和游戏渲染的是同一条曲线。
  实测这条路和真录像一致：30 个相位里**只有「宽度 0」那一帧读成 EMPTY**，
  而游戏里那一帧本来就没画东西（也是 `check_state_synth.py` 用的同一个约定）。
* 暂停键 / 倍速键的读数直接构造：那两个要模板文件和按钮渲染细节，
  而演示要验的是刻度表，不是再验一遍按钮识别。
* 开关：`--demo-speed`（每秒走几倍速的逻辑帧，调大就快进着看轴）、
  `--demo-bullet`（子弹时间，恒 6 帧/秒）、`--demo-max`（全程满费，走挂钟通道）、
  `--demo-pause N`（每 N 秒暂停 1.2 秒）、`--demo-res 宽x高`（默认 2558x1494，命中实测表）。
* 取时间的函数是**注入**的（`clock` 参数），所以 `tools/check_demo.py` 能塞一个假钟
  逐拍推演 —— 10 秒的戏一秒钟跑完，且结果完全确定。

### 19.5 演示里量出来的两件事

* **满费走挂钟时，整数帧号会 0/2 交替跳**：`Counter._clock` 把不足 1 帧的余量攒着，
  攒够才吐一帧，所以整数位在 0 和 2 之间摆。精确值是 `elapsed_f`：喂理想输入 3 秒，
  正好 90.000 帧（整数位却报 91）。**判满费准不准要拿小数位判，不能拿整数位判。**
* **费用周期边界上，计数器会把两帧并成一次 +2**（通道名 `wrap-missed`）：喂**理想**
  信号也一样出现，表现是「打轴器的轴晚 1 帧才触发」（总数是对的、位置在边界处差 1）。
  代码注释以前把这条归因于「采样漏了一拍」，但现在喂的是逐帧无漏的合成信号，
  说明至少还有**建模**上的成分（模型在周期末尾多出一个「画满」帧）。值得单独立项查，
  不要再用「提高采样率」解释它。
* 暂停段：演示里**一帧都不喂**，只把面板状态改成「已暂停」（数字按住不动，
  就是真实暂停的样子）；恢复时**不重新起锚** —— 相位在暂停期间没变，重锚等于白丢一帧
  （实测每暂停一次少记 1 帧，10 次就是 10 帧）。这一条也适用于真链路。

## 20. 采样线程会静默死掉：「莫名卡死」的根因、兜底与「重新校准」（2026-10-07）

### 20.1 结论先行

* 症状：面板一切「看起来正常」—— 「采样 1xx Hz」还在跳、ROI 预览还挂着最后一帧、
  游戏那边也确实在走，但**帧号不动了**。用户报的是「有些时候会莫名卡死」。
* 根因：`live.LiveMonitor.run()` 原来是**裸循环**。`_sample()` 只要抛一次异常
  （窗口被拖走 / 最小化时 BitBlt 失败、ROI 切出空数组、counter 里的断言……），
  这个 daemon 线程就**静默退出**了。它是 daemon，退出时没有任何提示；
  而面板是**另一个** `root.after` 循环在跑，于是「采样死了」和「采样活着」
  在界面上长得一模一样。
* 更糟：打包后用 `pythonw.exe` 跑**没有控制台**，traceback 连个地方都去不了。
* 所以修的时候三件事必须一起做，缺一个都不算修好：
    * **循环兜异常** —— 线程不再死；
    * **面板看得见** —— `stats.ticks` 心跳看门狗，停了就红字（20.5）；
    * **一键救回来** —— 「重新校准」/ F5（20.6）。
* 顺带修掉一个**一直是假的**功能：`set_layout(keep_elapsed=True)` 口口声声「保留已数帧数」，
  实际只搬了一个 `elapsed`，下一拍就被 `step()` 重算成 0（见 20.4）。

### 20.2 实测证据（录像 Desktop 2026.10.07 - 13.56.18.01.mp4，21 秒）

| 观测量 | 视频里读到的 | 说明 |
|---|---|---|
| 状态行 | 一直是「已暂停（条在动，按像素计数）」 | 这条是拿「最后一拍还活着」时的读数算出来的，线程死了它也不会变 |
| `采样 656 次` | **从头到尾一次没变** | 这就是证据：采样循环已经不再转了 |
| `采样 116.2 Hz` | 一直显示 116.2 | 也是最后一拍的**残留值**，不是实时值 |
| `面板 N Hz` | 48 / 58 / 60 / 62 / 64 / 65 / 66 / 67 / 76 之间跳 | 面板自己的 `root.after` 循环**还活着** |
| 游戏侧 | 正常（MAA 锁屏暂停，费用条在动） | 不是游戏的问题，是采集的问题 |

结论：**「面板 Hz 在跳」完全不能证明采样还活着** —— 它俩是两个独立的循环。
能证明的只有 `stats.ticks`（见 20.3）。

### 20.3 修法一：run() 每一拍兜异常，心跳独立记账

* `LiveStats` 加三个字段：
    * `ticks` —— **每转一圈 +1，不管这一拍读没读到画面**。这是「心跳」，
      也是看门狗唯一的依据；
    * `errors` / `last_error` / `last_error_t` —— 被兜住的异常。
      打包后没有控制台，不留给界面看就等于没有。
* `run()` 的循环体：每拍先 `ticks += 1`，然后在 try 里跑 `_sync_csv()` +
  `_sample()`；抛了就把 `misses` 加一、交给 `_on_error`，**然后继续转**。
* 连续失败时（`rate=0` 那种不配速的情况）让出 1ms CPU，
  别把核心烧在必然失败的循环上。
* `_on_error()` 做四件事：
    * 记账（`errors / last_error / last_error_t`）；
    * **只在 `misses == 1` 时打完整调用栈** —— 持续失败每拍打一遍会把控制台刷爆，
      而打包后本来就没有控制台；
    * **丢掉 `window` / `_grabber` / `_last_window_scan`** —— 采样里的异常绝大多数
      就是「窗口动了 / 换了进程 / 分辨率变了」这一类，缓存下来的句柄和 DIB 全不作数，
      全部丢掉，下一拍重新找一次窗口。多数情况下**不用人管就自己好了**；
    * `counter.resync()`：相位不可信了，重新起锚，不猜。
* 面板上多了一个 `心跳 N`（和 `采样 N 次` 并排）。这两个数的区别要说清楚：
    * 正常时两者相等；
    * **读不到画面的拍只涨心跳、不涨采样次数**。所以「采样 N 次冻住、心跳还在涨」
      = 采样线程活着，只是没东西可读；**两个一起冻住才是线程死了**。

### 20.4 修法二：`set_layout(keep_elapsed=True)` 以前是假的

* `Counter.step()` 每一拍末尾都用 `pixel_frames + clock_frames` **重算** `elapsed`。
  所以旧代码 `self.counter.elapsed = elapsed` 搬过去的值，下一拍立刻被 `0 + 0` 覆盖 ——
  表现就是「换个窗口 / 重新校准一下，数字从 0 重新数」。
* 新增 `Counter.adopt(other)`：把 `pixel_frames / clock_frames / _clock_frac /
  cycle_lengths / _cycle_seen / last_m` 一起搬过去，并**当场重算** `elapsed / elapsed_f`。
    * `cycle_lengths`（逐帧的费用周期长度）是按**帧**记的，和像素几何无关，
      换分辨率不该把「一费 N 帧（中位）」这个统计清空；
    * `last_m` 同理：读不到倍速时靠它沿用，换布局时清回 1.0 会在满费挂钟通道上
      按错误的倍速算一拍。
* 变异验证：把 `adopt` 换回 `self.counter.elapsed = old.elapsed`，
  `tools/check_recover.py` 立刻报 `before=58 after=0` —— 正是用户会看到的「重新数」。

### 20.5 修法三：面板看门狗（区分「游戏暂停」和「采样死了」）

* 盯 `stats.ticks`：变了就把 `_stall_since` 归零；没变、且还没记过，就记下当前时刻。
  于是 `stall_s >= STALL_WARN_S` 或**线程已经不在了**（`monitor.alive` 为假）
  就判「采样已停」。
* `STALL_WARN_S = 1.0` 秒不是随手拍的：正常采样 120Hz（心跳每 8ms 一次），
  1 秒 = 120 次心跳一次都没来，绝不可能是抖动；而 1 倍速下一个逻辑帧才 33ms，
  1 秒也远大于任何一次「游戏暂停」该有的样子。
* 判停之后**状态行转红**（`ERR` 色）写
  「状态 采样已停 N.Ns（原因）→ 点「重新校准」或按 F5」，提示行给出下一步动作，
  并说明**已经数出来的帧数不会丢**。
* 顺带修掉一个真 bug（`check_recover.py` 第 5 组抓到）：这一拍**没读到画面**时
  （`upd.result is None`），状态行原来**一个字都不改** —— 于是「线程刚被救活、
  但还没读到画面」的这段时间里，上一条红字「采样已停」会一直挂着，用户会以为没救活。
  现在这个分支会把状态行改成中性色的一句「采样正常，这一拍没读到画面（原因）」。
  * **2026-10-09 更新**：面板那一行「状态」整个删掉了（用户：「状态栏可以删掉」，
    见第 30 节）。上面这条红字现在写在常驻区的「告警：」行（`lb_warn`）；「没读到画面」
    那个分支改成**把告警行清空**（语义没变，还是「别让上一条红字挂着」），
    `tools/check_recover.py` 第 5 组的断言跟着改成盯 `lb_warn`。

### 20.6 「重新校准」按钮 / F5

* 语义是**重新对准**，不是清零（清零有单独那个按钮）：重找窗口 -> 按当前客户区重算 ROI
  -> 采样线程死了就拉起来 -> `counter.resync()`。全程**保留已经数出来的帧数**。
* 什么时候用它：游戏窗口被拖走 / 改了大小、换了分辨率、切了全屏，
  或者告警行红着说采样停了（看门狗会告诉你）。
* 重启线程时用的是 `start(reset_clock=False)`：**不重置时间基准 `_t0`**。
  理由很具体：重新校准往往发生在 `t` 已经走到几百秒的时候，重置 `_t0` 会让 `t`
  倒退回 0，而 `Counter` 的挂钟通道拿到一个**倒退的时间戳**就会算出负的 `dt`。

### 20.7 回归项

  `FlakyMonitor` 子类故意抛异常）。覆盖：异常不杀线程、异常后自愈、缓存被丢、
  心跳在读不到画面时照样涨、`adopt` 保住帧数、`keep_elapsed=False` 仍然清零、
  `recalibrate` 的四种情形、看门狗六项（Tk 不可用时 skip，不算失败）。

### 21.5 `_fit_window()`：最下面那行为什么会被切

* 现象：面板底部「Tab 切 ROI | 方向键移动…」那行**只露半行**，被切在窗口外。
* 根因（实测）：窗口尺寸是 `__init__` 里**照占位文本**算一次就定死的
  （`win_h = min(max(root.winfo_reqheight(), 640), ...)`）。运行时那些会换行的行
  （性能行 / 告警行 / 费用周期）字一长就多占一行，而**窗口高度不会跟着变** ——
  实测那一拍内容需要 957x1450，窗口却还是照占位文本定的高度。
* 修法：`_tick_body` 里每 0.5 秒核一次 `winfo_reqheight()`，比当前窗口高就长高，
  上限 `屏幕高度 - 20`。**只长不缩** —— 缩会在文本忽长忽短时来回抖。
* 验收：出图那次窗口从 957x1450 自己长到 979x1530，帮助行三行（含换行）全部可见。

## 22. 录像文件 / 读窗口：只换掉「帧从哪来」那一环（2026-10-08）

两条链路共用同一套「自动对齐 + 量条槽 + 搜按钮」（`video.VideoSource._calibrate`
那一段），采样、计数、打轴、CSV 也**一行都没改** —— `live.LiveMonitor` 只管
「怎么数」，`_resolve_window` 每一拍重新问「客户区在屏幕哪儿」，所以窗口被拖走是自动跟随的。

读窗口的用户流程（`ui.MonitorApp.read_window` / `start_window_calib` / `toggle_window_count`）：

    打开录屏（播放器）→ 置顶 → 点「读取窗口…」选它
      → 自动校准（没把握就点「框选费用条」手动圈）
      → **点「开始计数」** 才起采样线
      → 中途「重新校准」/F5：重新对齐，**帧数保留**；本来在数就接着数

### 22.2 为什么窗口链路必须另开一份校准表

同一个客户区尺寸下，**游戏窗口**和**播放器窗口**的三条 ROI 差着几百像素：播放器里
画面还被缩放过。混在一张表里必然互相覆盖。所以键取 `进程名|客户区宽x高`
（`window.window_key`），文件是 `window_calib.json`。

实测（本机 VLC 放 2560x1600 的录屏、VLC 客户区 1378x844）：

| 项 | 值 |
|---|---|
| 画面缩放 | 0.4777 倍（2560x1600 -> 1223x764） |
| 画面里的游戏客户区 | 1218x688 @(85,50)（窗口客户区坐标） |
| 费用条真值 | x=1189 宽 114 高 17（条槽真宽 114.2 px） |
| `layout_for(1378,844)` 的预测 | 横向偏约 60 px、纵向偏约 84 px、条宽预测 129 px |

「客户区」这个词在两条链路里含义不同，别混：**窗口**链路里 `src.size` = 窗口客户区
（抓屏的坐标系），`src.client/offset` = 画面里那块游戏客户区；**录像**链路里
`src.size` = 视频画面，`src.client/offset` = 画面里那块游戏客户区。

### 22.3 手动框选：一条硬关系反推客户区

`window.layout_from_bar_box`：**条槽宽 = 180 x s x edge**（s = 显示出来的客户区的缩放，
edge = UI 缩放的边缘系数）。所以框一定要**贴住费用条的两端**（框宽 = 条槽宽），高度随便
（只取中心线，ROI 固定 17 行）。反推出 s 之后客户区 = 1920s x 1080s，原点由框的位置定死，
最后把费用条 ROI 按框原样钉死（左边缘用框的、宽用框宽）。

面板上那条路是「全屏半透明遮罩上拖一个框」（`ui.MonitorApp.box_bar`）：拿到的是**屏幕**
坐标，要减掉 `client_rect(hwnd)` 的原点才是客户区坐标 —— 这一步在 `_box_done` 里。
框跑出窗口外面会直接报错，而不是算出一份假布局。

### 22.4 自动对齐要「网格搜索」，不能把半径一次开大

`align.offset_from_frames` 的亮/暗阈值是按**抽出来的这一块**的 p10/p99 定的。把搜索半径
一次开到 ±300，块里 99% 是背景（实测播放器窗口里费用条只占 0.4% 的像素），p99 掉到背景
电平上，阈值失效、阶跃消失，对齐整个崩。

所以每一格**单独抽一小块、单独定阈值**，在外面串成网格：`WINDOW_GRID_R=300`、
`WINDOW_GRID_STEP=60`（步长要 < 2 x `DX_RANGE`，否则格子之间会漏掉条）、`GRID_TOP_N=12`
个候选再逐个做「条在不在动」的自检（`_verify_bar`）。判据只有一条：费用条是画面上
**唯一**一种「左边缘固定、右端在长」的横线。播放器的音量条 / 进度条、任务栏那条亮线
都能仿「横线」，但仿不了「动」—— 实测那几条假线的阶跃分比真条还整齐。

### 22.5 白电平：p99（所有像素）-> p99.9（每列最大值）

这是本轮最关键的一处修复。窗口里那一块 99% 是背景，`max(p99(所有像素), ...)` 里的
「所有像素的 p99」掉到 55（就是条槽的灰底）—— 于是**灰轨道被当成亮点**，整块变成
「完美阶跃」，而且**纵向位置完全不受约束**（实测 dy 偏 5 px，读条读到 0）。

改成 `max(p99(所有像素), p99.9(每列最大值))` 之后，填充（占 0.98%）重新成为最亮档，
`_detect_offset` 精准命中真值 (dx=-60, dy=-84)。

注意**暗电平必须保持「所有像素的 p10」**：曾经一起改成 colmax，薄条块会 hi-lo=0 自毙。

### 22.6 踩过的坑

| 坑 | 现象 | 修法 |
|---|---|---|
| `_detect_offset` 里 `MIN_ALIGN_STEP` 没定义 | NameError，自动对齐这条路**从来没跑过** | 补上常量 |
| `_size_of(client)` 四元组陷阱 | 顺手把 `WindowInfo.client` 的 `(x,y,w,h)` 整个传进去，键就拼错了 | `_size_of` 认两种：`len>=4` 取后两位；检查脚本里加了一条断言守着 |
| VLC 会自己改窗口大小 | 窗口客户区在播放中从 1378x844 变成别的，尺寸一对不上校准就作废 | 起 VLC 必须带 `--no-qt-video-autoresize`（`--no-qt-updates-notif --no-video-title-show --video-on-top --loop --volume=0`） |
| 进度先跳到「就绪」再退回「自检」 | 基类在收尾时喊 `ready`，而自检还没跑 | `WindowSource._say` 在 `_prepare` 期间按住 `ready`，自检完自己喊 |
| 校准完采样线程是本该停着的 | 面板看门狗会把它当成「采样已停」报警 | `_tick_body` 里 `idle = _src_kind=='window' and not _window_started`，idle 时不报警 |

### 22.7 面板上两条容易改坏的语义

* **校准完不自动跑**：`_adopt_window` 只把监视器换上去，`mon.start()` 留给用户点
  「开始计数」。所以 `_window_started` 这个标志同时管两件事：按钮文案、和看门狗要不要报警。
* **重新校准保留帧数**：`_adopt_window` 里把旧的 `Counter` 用 `Counter.adopt` 接过来
  （只搬 `elapsed` 会被下一拍 `pixel_frames + clock_frames` 覆盖，见第 20.4 节），
  本来在数就 `start(reset_clock=False)` 接着数 —— 时间基准不能倒退。

### 22.8 回归项

* `python tools/check_window.py` —— 27 项，假屏幕跑真实采样循环：框选反推客户区、
  按比例缩放、校准表分键、自动校准自检、**一费 = 30 帧**、手动框选钉 ROI。
* `python tools/check_ui_window.py` —— 20 项，把整个面板建起来跑：校准完**不**自动跑、
  点开始才跑、清零后从 0 数且总数 = 画面走过的逻辑帧、一费 30 帧、框选的屏幕坐标 ->
  客户区坐标、重校准保留帧数、保存校准落盘、切回实时。
  写这条断言时踩过一次：**别拿「挂钟走了 3.6 秒」当真值** —— 计数器是按「条在当前这一费
  走到了第几帧」起锚的，第一拍落在周期第 8 帧的话总数就天然少 8；要让真值固定下来，
  必须**先采一拍再清零**（这样 `mark_zero_start` 才知道清零那一刻的相位）。
* 跑之前先把 `tools/check_window.py` 的帧源换回真屏幕就能当冒烟测：起 VLC
  （带上面那串参数）-> seek 到 12.5s -> `set_topmost` -> `WindowSource` 校准 ->
  `WindowMonitor.start()` 跑 30 秒，`cycle_lengths` 应当恒为 30。

## 23. 三件 UI 的状态判定：怎么才不在关卡外乱计数（2026-10-08）

**问题（用户报的）**：暂停键 / 倍速键 / 费用条三个读数「各自单看」都会被「不在关卡里」的
画面骗。三种骗法全都实测到了：

| 读数 | 骗法 | 实测 |
| --- | --- | --- |
| 费用条 | 菜单 / 仓库 / 切场景时条 ROI 压在别的高亮 UI 上，读出一条**宽度恒定**的假白条 | 2026-10-05 那段会话的 CSV：`fill=154` 连着 3.1 秒、`fill=215` 连着 1.5 秒，状态 TRACK |
| 暂停键 | 那些画面上 ROI 里只有细笔画 / 底色，亮点占比够高 | 关卡外的帧：箭头带亮点占比 **0.028~0.093**（旧判据 0.02 直接放行） |
| 倍速键 | 同上，被读成子弹时间 >>> | 满费时按 6 帧/秒算，速率差 5 倍 |

### 判据：不看「亮点占比」，看「**画出来没有**」

`rel_threshold` 是跟着画面自己的电平走的，暗画面上细笔画很容易被放大成「亮点」。
所以新增 `features.erode3` / `solid_frac`：对亮块做 **3x3 全邻域腐蚀**（自己和周围八格
都亮才留下），细笔画 / 噪点全没了，只有**真画上去的实心形状**（▶ / ❚❚ / 箭头）活得下来。

实测分布（`tools/check_ui_state.py` 逐帧跑出来的）：

| 场景 | 暂停键形状带的实心占比 | 倍速箭头带的实心占比 |
| --- | --- | --- |
| 关卡内（22-20-20，2940 帧）| min 0.0434 / 中位 0.0439 / max 0.2184 | 真箭头（991 帧）min **0.0304** / 中位 0.0317 |
| 关卡内（23.53，1895 帧）| min 0.0315 / 中位 0.0466 / max 0.2348 | — |
| 关卡外（加载 / 选关 / 桌面 / OBS 窗口 / 黑屏）| ≤ **0.0146** | ≤ **0.0135** |

阈值取两个数中间的 `PAUSE_GLYPH_MIN = ARROW_SOLID_MIN = **0.020**`：往下离噪声 1.4~1.5 倍，
往上离真值 1.5~2.2 倍。倍速箭头那个比值实测 **2.25**（真箭头 0.0304 / 噪声 0.0135）。

为什么不是 0.012：一开始取 0.012，离噪声上限 0.0135 只有 6% —— 噪声稍微抖一下整段就被
读成子弹时间。提到 0.020 之后，22-20-20 里有 8 帧（帧号 2950~2957）从「子弹时间」变回
「没画箭头」，`check_ui_state.py` 把这条钉住了。

### 关卡判定：进关卡必须看到 HUD

`state.Counter` 现在两道闸：

    bar_moving = 条宽/状态这一拍变过
    hud        = 暂停键画着（drawn） 或 倍速键画着（数字 / 实心箭头）
    进关卡  : 条在 AND hud                    <- 菜单的假条进不来（它是死的，画不出 HUD）
    留在关卡: 条在 AND (hud OR 条这一拍在动)   <- 兜住关卡内 HUD 偶尔读不到的一两拍

菜单压出来的亮块**动不了**（实测 fill 恒定），所以即便它让条读数动起来，
进关卡那一步也过不去 —— 这就是根治「在别的界面也计数」的那条规则。
实测 22-20-20 的开头（第 0~52 帧，进关卡前的加载画面）和片尾（第 2944 帧之后）
一共 110 帧：**一帧都没记**。

### 子弹时间不再用「时间闸」

上一版加过一条「倍速数字消失 ≥0.25 秒才算子弹时间」，理由是「数字会每 5 帧闪一次」。
追下去发现**那个『闪』是假象**：它是拿一段**录桌面的**录像、用 `layout_for()` **预测**的
ROI 扫出来的 —— 游戏窗口并不在那个位置（实测：那批帧里数字占比在 1%~33% 之间乱跳、
暂停键帧帧不同，把 ROI 裁出来一看按钮压根不在假定的条带里）。

对齐好的录像里（22-20-20）子弹时间的进出都是**一拍之内**完成的：

| 帧号 | 事件 | 数字带占比 | 箭头实心占比 |
| --- | --- | --- | --- |
| 99 -> 100 | 2X -> >>> | 0.2721 -> 0.0014 | 0.0499 -> **0.0316** |
| 1090 -> 1091 | >>> -> 2X | 0.0014 -> 0.2661 | 0.0315 -> 0.0501 |

所以时间闸只会把每次进子弹时间的前 0.25 秒（1 倍速 7.5 帧、2 倍速 15 帧）按正常倍速
记错 —— 那正是「一费 30 帧变成 62 帧」这一类偏差的来源。**删掉**，只认实心箭头。

### 倍速数字画着、但认不出来：沿用上次

「有数字」和「认得出是几倍速」是两件事：HDR 录像 / 过渡字形下 `corr_2x` 会低于
`CORR_2X_MIN`，`m` 读成 nan。这时按钮**确实画着**、画的又不是子弹时间的箭头，
所以不该冻结 —— 沿用上次读到的倍速（`last_m`，初值 1X）继续数。
实测这种读数占真实会话 **2898 / 20436 拍**（`speed-low-conf`），冻结等于把满费期间的
帧操整段丢掉。真正「什么都不画」时才冻结（`warn='speed-unknown'`）。

### 验收

| 检查 | 结果 |
| --- | --- |
| `tools/check_ui_state.py`（新增）| 合成：死的 / 在动的假条 + HUD 没画 = 0 帧；对照（同样的条 + HUD 画着）照常记 |
| 同上，实测帧 | 关卡外 110 帧记 0 帧；关卡内暂停键 0 帧缺失；箭头与噪声比值 2.25 |
| `tools/check_speed_mix.py`（扩了 3 个用例）| 新增「关卡外假白条」「关卡外假白条在动」「2X 数字糊了」，15 个用例全过 |
| A/B：把「进关卡要不要看 HUD」换回旧写法 | 4 段录像总帧数**完全一样**（不丢帧）|
| 原有 11 个检查 | 全过（采样 / 校准 / 回费速率 / 录像链路 / 窗口链路 / 面板）|

面板上把实心占比也印出来了：`按钮 ratio=0.064 solid=0.044 已暂停` —— 调阈值时不用猜。

## 24. 录像「完全识别不到」：表里那份 ROI 没人校验（2026-10-08）

### 24.1 结论先行

录像链路有一条**快路径**：`video_calib.json` 里若记着同画面尺寸的 layout，就照抄那三个 ROI、
跳过「自动对齐 + 量条槽」（那一步要几秒到几十秒）。这条快路径以前**一个字都不校验**。

而校准表是按**画面尺寸**归档的，画面尺寸跟「游戏窗口在画面里的位置」压根没关系 ——
用户本机所有桌面录像都是 2560x1600，游戏窗口却在好几个不同的地方出现过：

| 录像（本机，全部 2560x1600） | 游戏窗口在画面里 |
| --- | --- |
| Desktop 2026.10.05 - 11.01.51.01.mp4 | 1920x1200 @(627,198) 那一档 |
| Desktop 2026.10.07 - 13.56.18.01.mp4 | 另一档（条槽左端比表里偏 +29px） |
| obs 2026-10-04 22-20-20.mp4 | 又一档（偏 +41px，纵向还差 56px） |

于是**每一段录像都在错位的地方读条** → 条永远 EMPTY → 计数器 0。用户看到的就是
「录像完全识别不到」。

### 24.2 判据：只有一条硬事实

layout 的约定是 `bar.x = 条槽左端`，而费用条的填充是**从条槽左端开始往右长**的 ——
所以「白块最左那一列」应当正好压在 ROI 的左边缘上。这条关系不用模型、不用标定：

    judge_bar_layout(strip, layout, left_col) -> (True / False / None, 说明)
        取整段 0% / 50% / 90% 三处各 8 帧（开头常是菜单，只取一处会误判），
        每帧算「白块左端 - ROI 左边缘」：
            看不到白块             -> None（没法判断，不能据此否掉一份 ROI）
            中位数偏出 VERIFY_LEFT_TOL = 5px -> False（错位，去重量条槽）
            左端自己抖动超过 3px    -> False（那不是条槽）
            否则 True

四段录像实测的偏移：**+29 / +39 / +0 / +41**（px）—— 只有 `00.37.30.04` 那段通过。

### 24.3 修法一：照抄之前先自检；自检不过**只丢 ROI，不丢客户区**

`_verify_layout` 说「不对」时丢掉的只是那份 ROI（重新量条槽），表里记的 `client` / `offset`
**留着当预测锚点** —— 重量条槽的探针框就是按它们算出来的预测位置往外扩一圈。
（客户区那一对值本身也可能是别的窗口几何留下的，但「假设画面就是客户区」更离谱：
见 `client_from_slot` 的注释，实测差 160px。）

重量还是失败时，再赌一次完全自动的 `_detect_offset`（拿整幅画面找相位阶跃）。

### 24.4 实测 A/B（四段真录像，带 templates 跑完整段）

| 录像 | 总帧 | 照抄表里 ROI | 先自检 | 自检结论 |
| --- | --- | --- | --- | --- |
| Desktop 10.07 13.56.18.01 | 1262 | **0** | **47** | 偏 +29px → 否掉 → 重量出条槽 x=2363 宽 178 |
| Desktop 10.05 11.01.51.01 | 2904 | 4 | 5 | 偏 +39px → 否掉；重量没看见白块（开头一直在菜单 / 暂停）→ 退回预测值 |
| Arknights 10.04 00.37.30.04 | 1197 | 52 | 52 | 偏 +0px → 通过，照抄（这段以前就是好的）|
| obs 22-20-20 | 3001 | 0 | 0 | 偏 +41px → 否掉；重量同样没看见白块 |

第三行是**正对照**：自检没有把好 ROI 误杀，也没变慢（1~2 秒就过）。
最后一行说明自检只能「否掉错的」，救不回「自动量不出来的」—— 那种就要手动框选。

### 24.5 修法二：手动框选 + 参照物（`boxpick.py` / `ui.BoxPicker`）

用户的原话是「改成手动截取，手动截取不准确，需要参照物」。为什么手拖不准：
2560x1600 的画面缩到屏幕上拖框，屏幕上 1px = 画面 1.5~2px = **3~4 个逻辑帧**的相位误差 ——
只靠眼睛，做不到「一费 30 帧」。所以给三样参照物：

| 参照物 | 是什么 | 解决什么 |
| --- | --- | --- |
| 刻度尺 `guide_image` | 画面上叠一把**橙色 30 等分刻度尺**（30 格 = 一个费用周期），蓝框标出右上角两个按钮的预测位置 | 让用户对着刻度对两端，而不是对着空气 |
| 放大镜 `magnify` | 框内那一条带放大（横向 x3、纵向拉得更狠）；红 / 绿竖线 = 框的左右边缘，蓝线 = `read_bar` 真正取样的行 | 白块左端压没压在红线上，一眼可判 |
| 吸附 + 最满的一帧 `snap_box` / `fullest_frame` | 「吸附左端」把左边缘钉到白块起点；「跳到最满的一帧」让白块右端 = 条槽右端 | 左右两端都不用猜：那是画面上本来就有的两把尺子 |

刻度尺是**参考**不是答案：它按画面尺寸当成客户区推出来，实测在这一段录像上比真条低了约
110px（游戏窗口不在画面原点）。真正定相位的是吸附。

面板入口：录像那一行「框选费用条」→ 参照图窗口（拖框 / 参照帧滑块 / ±1 帧 / 跳到最满的一帧 /
像素级微调 / 吸附左端）→ 「用这个框」重抽流（几十秒，后台）。

框选那条路**不查表、也不量条槽**（框本身就是从像素上读出来的位置），但会：

1. 按框宽反推客户区（条槽宽 = 180 x s x edge），再用 `_fit_buttons_coarse` + 模板搜两个按钮；
2. `_snap_bar_left` 把左边缘吸到白块起点；
3. `_verify_layout` 自检一遍（框没贴住条槽会在面板上提示「可以重新框一次」）；
4. `save_manual=True` 时记进校准表 —— 下次同尺寸的录像**先自检再套用**。

框选用的缓存目录带 `_barbox` 后缀：手动框出来的 ROI 和自动量出来的不是同一套，
共用一个目录会互相覆盖（切一次重抽一次）。

### 24.6 一个真踩到的坑：`fullest_frame` 一个白块都扫不到

「跳到最满的一帧」= 扫整段、找白块最长的那一帧。修之前它是这么取剖面的：

    row = np.median(整块探针框的所有行)     # 探针框 = 条 ROI 上下各留 4 行，共 26 行

而条是**很细的一条**：实测那段录像里白块只占中间 4~8 行，剩下的行是轨道 / 背景 ——
中位数直接把白块稀释成轨道灰，`fill_run` 返回 None，于是「跳到最满的一帧」永远 -1。

改成只看**条带那几行**（`band_rows_of`，和 `read_bar` 同一套 `BAR_BAND_TOP/BOTTOM`）：

| 取剖面的方式 | 采样帧里扫到白块的 | 「最满的一帧」|
| --- | --- | --- |
| 整块探针框取中位数 | 0 / 106 | -1（永远找不到）|
| 只取条带行（修后）| **104 / 106** | **204** |

修完在真录像上：白块左端恒为 2363（= 钉住的 ROI 左边缘；整段只出现 2363 / 2367 两个值），
右端 2371 → **2540**，而 2540 - 2363 + 1 = 178 = 量出来的条槽宽 —— 左右两端互相印证。

  自检判据的每条边界（通过 / 偏 29px 否掉 / 反向偏 6px 否掉 / 一个白块都没有 = 没法判断 /
  左端抖动否掉）、框宽 -> 客户区换算（180px -> 1920x1080、239px -> 2549、框越界报错）、
  吸附左端（右移 12px、右端不动、条空着不动、白块太远不吸）、参照图与放大镜尺寸、

## 26. 清零「只有开始计数时才生效」（2026-10-09）

### 26.1 症状

用户原话：「清零功能有点问题，开始计数时才生效暂停期间没用」。

### 26.2 根因：面板读的是一份**缓存读数**，而它只在「这一拍真读到画面」时才刷新

`Counter.elapsed` 在清零后确实立刻变 0（复现脚本里打印过：`counter.elapsed=0`），但面板大数字
读的是 `monitor.latest.result.elapsed` —— 而 `latest` 只在 `_sample()` 真的走完一遍采样时才被替换：

| 场合 | 这一拍会不会来 | 结果 |
| --- | --- | --- |
| 实时游戏窗口（采样线程一直跑）| 会 | 清零正常 |
| 读窗口：校准完**还没点**「开始计数」| 不会（线程没起）| 数字挂着旧值 |
| 读窗口：点了「停止计数」| 不会（线程停了）| 数字挂着旧值 |
| 录像：**播放暂停** | 不会（`_sample_locked` 直接 `replace(latest, ...)` 返回旧的 `res`）| 数字挂着旧值 |

复现（`DemoMonitor`，暂停计数状态）：清零前后 `latest.result.elapsed` 一直是 **8**，而
`counter.elapsed` 已经是 **0**。差的就是这一份缓存。

### 26.3 修法：两处一起

1. `LiveMonitor.reset()` 收尾调 `rezero_latest()` —— 把缓存读数里的帧号（`idx` / `delta` /
   `elapsed` / `elapsed_f`）按回 0。**只动帧号**：条宽 / 状态 / 模式是「这一刻画面长什么样」，
   和第几帧无关，照旧留着（否则面板会闪一下"条是空的"）。
2. `MonitorApp.clear_count()` 里再调一次 `_show_zero()` —— 立刻把大数字 / 时间行按回
   `0` / `00:00.00`。这一条兜的是 `latest.result is None` 的情况（校准完还没读到任何画面），
   那种情况下第 1 条无从下手。

为什么"先按回 0"不算骗人：清零的语义本来就是「从这一刻起从 0 数」，下一拍真读到画面时算出来的
也是 0 起步，两边一致。

### 26.4 回归项

* `python tools/check_video.py` —— **31 项**（原 28）。第 3 组「播放暂停」里新增 3 项：
  暂停中清零 -> 计数器归 0、**缓存读数也归 0**、暂停期间再采一拍仍是 0（没被采样覆盖回去）。
* `python tools/check_ui_window.py` —— **22 项**（原 20）。第 2b 组新增 2 项：故意把大数字写成
  `123`，再 `clear_count()`，看它有没有立刻变 `0`（不等下一拍）、时间行有没有归 0。

### 27.2 置顶为什么必须「重钉」

读窗口这条链路抓的是**屏幕上那块像素**，目标窗口被压住一角，压住的那块读到的就是别人的
画面 —— 费用条在右下角、按钮在右上角，压住等于整条链路瞎了。而「置顶」这个状态实测
**两种都会掉**：

1. 播放器切全屏 / 换下一段视频会**重建窗口**，新窗口不带 `WS_EX_TOPMOST`；
2. 我们自己这个面板**也是置顶的** —— 两个置顶窗口里最后被激活的在上面。用户点一下面板
   （点「开始计数」就得点），面板就压到播放器上面了。

所以 `_keep_pin()` 每 `PIN_KEEP_S = 0.7` 秒调一次 `win32.set_topmost(hwnd, True)`
（`SetWindowPos(HWND_TOPMOST)`，**不动大小、不抢焦点**）。为什么是 0.7 秒而不是每拍
（8ms）：这一条防的是「掉置顶」，不是「差半帧」，0.7 秒足够跟得上人的点击；每拍都去
`SetWindowPos` 反而会让目标窗口在窗口管理器里反复重排。

### 27.3 三条「不闷着」的规矩

| 情况 | 面板做什么 | 为什么 |
|---|---|---|
| 句柄失效（窗口被关 / 播放器重建了它）| 放开置顶 + 红字「点『换窗口』重新选一个」| 不**自动**换窗口：换窗口要重新校准、帧号从头数，那是用户的决定 |
| `set_topmost` 返回失败 | 提示「系统不让置顶，请手动设『总在最前』」| 典型原因是目标窗口以管理员身份在跑，UIPI 不让普通进程去动它 |
| 面板自己压住了目标客户区 | 窗口那一行红字「⚠ 面板压住了目标窗口」| 这条必须当面说：抓到的就是面板的灰色，计数会卡在某个帧号上，用户看不出为什么（冷启那段「莫名卡死」就是这么来的）|

提示只弹一次：`_note_pin` 拿 `self._pin_noted` 去重，否则 0.7 秒一遍会把提示行刷爆。
「面板压住窗口」这一条的判据是 `_pin_overlap()`：把面板的屏幕矩形和目标窗口的**客户区**
矩形做相交测试（客户区会随窗口被拖走而变，所以每拍重算）。

### 27.4 取景器例外

`_own_dialog_open()` 遍历 `root.winfo_children()` 找 mapped 的 `tk.Toplevel`，开着就
**这一拍不抢置顶** —— 「框选费用条」那个取景器本来就是要盖在目标窗口上面让用户对着参照
图圈的，把目标窗口抬上来反而会把取景器盖住。

### 27.5 回归项，以及一处检查自己的 bug

`tools/check_ui_window.py` 当时 **28 项**（现在是 32 项，见第 28.4 节），新增第 5b 组
（置顶重钉）、5c 组（面板遮挡告警）、5d 组（取景器不抢置顶）。

## 28. 置顶：面板每 0.7 秒被盖回去一次（2026-10-09）

### 28.1 症状（实测录像 `Desktop 2026.10.09 - 20.13.34.11`，8.5 秒）

拿媒体播放器放全屏录屏 → 读取窗口 → 面板摆左下角。对每一帧数「面板那块背景色
`(20,19,22)` 的像素数」，就能看出面板在不在：

    0.0~2.8s 隐藏 | 2.9s 露出 0.2s | 3.1~4.1s 隐藏 | 4.2s 露出 0.1s
    4.3~6.4s 隐藏 | 6.5~7.1s 露出 **0.7s** | 7.2~8.5s 隐藏

露出的那 0.7 秒正好等于 `PIN_KEEP_S`。同一段录像里媒体播放器的客户区是 **2560x1539**
（面板自己印的），也就是整块屏幕 —— 面板怎么摆都在客户区里。

### 28.2 根因：置顶是一「层」，同一层里最后抬起来的在最上面

`_keep_pin` 每 0.7 秒对目标窗口调一次 `SetWindowPos(HWND_TOPMOST)`。这一步干两件事：
把窗口标成置顶，**并把它抬到置顶那一层的最上面** —— 于是我们自己的面板（也是置顶的）
被压下去了。用户点一下面板、面板露一次脸，0.7 秒后又被盖回去。

### 28.3 修法两处

1. **钉完目标顺手抬面板**：`_keep_pin` 里 `set_topmost` 成功之后紧接着调
   `_raise_panel()` → `win32.raise_window(顶层句柄)`（`SetWindowPos(HWND_TOP)`，只改本层
   Z 序，不动「是不是置顶」）。净效果：目标在所有普通窗口之上，面板在目标之上。
   句柄要先用 `win32.top_level(root.winfo_id())` 换一次 —— Tk 的 `winfo_id()` 给的是里面的
   `TkChild` 客户窗口，真正排 Z 序的是它的父窗口（实测 `0x1a0dbc -> 0xa70d2e`，class 从
   `TkChild` 变 `TkTopLevel`）。`start_window_calib` / `toggle_pin` 里也补了同样的顺序。
2. **遮挡告警的判据从「面板 ∩ 客户区」换成「面板 ∩ 三个 ROI」**（`_roi_hits()`）。
   全屏播放器的客户区覆盖整块屏幕，按客户区判会**天天误报**（上面那段录像就是）；
   真正会把读数弄错的是面板压住了**费用条 / 暂停键 / 倍速键**自己 —— 那块像素抓到的
   是面板的灰色。告警文案会点名是哪一个被压住了。

### 28.4 回归项

`tools/check_ui_window.py` 现在 **32 项**：

* 5b 组新增「钉完目标顺手把面板抬回来（不然面板每 0.7s 被盖一次）」；
* 5c 组重写成三条 —— 压住费用条要告警、**在客户区里但没压住 ROI 不误报**、
  整个挪出客户区也不报警。

新增 `tools/check_win_zorder.py`（**6 项**，本机实测）：开两个 2x2 的小窗口真演一遍，
用窗口管理器自己的 Z 序（从最顶上那个窗口沿 `GW_HWNDNEXT` 往下数）验，不问坐标：

| 步骤 | 期望 | 本机实测（序号小的在上面）|
|---|---|---|
| 钉 A + 抬 A | A 在 B 上面（bug 那一幕）| A=14 ｜ B=15 |
| 抬 B | B 压到 A 之上 | A=15 ｜ B=12 |
| 再钉一次 A | A 又跑到上面（所以必须再抬一次面板）| A=14 ｜ B=15 |
| 再抬一次 B | B 回到上面 | A=15 ｜ B=12 |
| 只抬 `TkChild` | 抬不动 Z 序（必须换成 `TkTopLevel`）| A=15 ｜ B=12 |

顺带钉死了那条事实：`winfo_id()` 给的是 `TkChild`、`top_level()` 给的父窗口是 `TkTopLevel`。

## 29. 读数管线一处看全：卡顿 / 漏帧到底会不会被「校准」（2026-10-09）

### 29.1 一拍里发生什么（`live.LiveMonitor._sample`）

| 步 | 做什么 | 关键细节 |
|---|---|---|
| 1 | 找窗口、取客户区矩形 | 每拍重问一次，窗口被拖走自动跟随 |
| 2 | 一次 BitBlt 抓「三个 ROI 的外接矩形」 | 一次抓屏 ≈3ms 固定开销，分三次抓翻倍 |
| 3 | 内存里切三块、各自转灰度 | 只转 ROI（6.8 万像素），不转外接矩形（53 万）→ 省 6.6ms/拍 |
| 4 | 提特征 | 费用条＝白块填充宽度；暂停键＝实心占比；倍速键＝数字带 / 实心箭头 |
| 5 | `state.Counter.step` | 见 29.2 |

### 29.2 两条通道

* **像素通道**（条画着）：把「累加器相位 → 应该画多宽」的曲线和实测宽度对齐，取前进
  帧数 k。相位是**绝对量** —— 这正是「漏采几拍也不会少记」的原因：条画到哪就是哪，
  不看增量，也和倍速无关。
* **挂钟通道**（满费，整条换灰底、相位被游戏钉在 0）：速率 = 子弹时间 6 帧/秒，或倍速键
  上的数字 × 30；**带小数余量**（`elapsed_f`）。两个都读不到就冻结，绝不猜。

### 29.3 三种「没跟上」

| 情况 | 会发生什么 | 会不会自己校准 |
|---|---|---|
| 采样慢了几拍（卡顿）但条还看得见 | 这一拍 `_resync` 要的 k 超过物理上限（60 帧/秒 × 本拍间隔）→ 判 `pixel-jump` 扔掉 | **会，一帧之内**：被扔的这一拍把时间攒进 `_since_accept`，下一拍上限就够用（用 dt 当分母会死锁，见 `state._pixel` 注释） |
| 条读不出来（被遮挡 / 匹配失败 / 暂停中画面里没条） | `bar-reject`，delta=0；连续超过 `REJECT_RESYNC_SECONDS` 就按当前读数重新起锚 | 重新起锚。丢掉的帧无法证明，宁可少记不猜 |
| 整块画面读不到（窗口最小化 / 找不到 / 太小） | `Counter.resync()`：丢弃增量、以当前读数重新起锚；这段时长单独记进 `stats.unreadable_s`，`resyncs` +1 | **不补**。面板上「读不到 x.x 秒」就是这段时间，总数是不完整的 |

一句话：**条看得见就一定自愈**（像素是绝对量）；**条看不见只重锚、不补帧**。

### 29.4 卡顿跳变能补多大（合成信号 + 真 `Counter` 实测，2026-10-09）

造法：条停在某一帧、卡 200ms（这期间我们的采样照样在跑、读到的都是同一帧），然后
**直接跳到**第 (停住帧 + jump) 帧 —— 中间那几个逻辑帧游戏根本没画出来（就是「卡了一下，
下一帧条跳过去好几格」）。对照实验是「正常一帧一帧画过去」，两条时间轴最后条停在**同一格**，
所以最终数字应该一样：

| 卡住的位置 | +1 | +3 | +4 | +10 | +15 | +16 | +20 |
|---|---|---|---|---|---|---|---|
| 归零那一帧（条还是空的，读数 EMPTY）| 一致 | 一致 | 一致 | 一致 | 一致 | 一致 | 一致 |
| 有宽度的一帧（读数 TRACK，条冻住）| 一致 | 一致 | 一致 | 一致 | **少记 15** | **少记 16** | **少记 20** |

* 「一致」＝ 一帧不差地补回来：恢复的第一拍先判 `pixel-jump` 拒掉（+0），**下一拍**
  按 `+jump` 收下。中途不会一格一格追（不会出现 02 / 03 / 04），是**直接跳到位**。
* 「少记」＝ 相位模型连续对不上超过 `REJECT_RESYNC_SECONDS = 0.2` 秒 → 重新起锚，中间那
  几帧永远丢掉。**只会少记，绝不会多记**（那条链路从不用挂钟补帧，见 29.2）。
* 卡在空条那一帧更宽松：那段时间走的是关卡判定那条分支，**不累加 `_reject_s`**，所以
  「重锚」的 0.2 秒计时压根没在走 —— 实测跳 +20 也照样补齐。
* 一句话：**跳变 ≤ 约 12~15 帧（1X 下 0.4~0.5 秒的游戏时间）一定补齐；再大就只重锚、
  那一段少记。** 上限由 `60 帧/秒 × 0.2 秒 + DFILL_SLACK(3 帧)` 这个式子定死。
* 具体到你问的那一次（01 帧 → 卡 → 05 帧，跳 4 帧）：面板最后显示 **05**，4 帧一帧不差；
  区别只是「卡在空条那一拍恢复时立刻 +4」还是「卡在有宽度的一帧先拒一拍、8ms 后 +4」。

## 30. 满费小数点：「数字一变，整块面板跟着跳」（2026-10-09）

用户报的原话是「帧数显示小数点 ui 突然变化」。现象是满费那几秒里，大数字一印出两位小数
（`123` -> `123.45`），右边那三行（逻辑帧 / 游戏内时间 / 状态）会整体往右挪一下。

### 30.1 两个叠在一起的原因

1. **格式跟着「这一拍走的哪条通道」走。** 满费那些拍在「挂钟通道」和「倍速未知 -> 冻结」
   之间来回切，原来只在 `mode.startswith('clock')` 时才印小数，于是数字在 `123` /
   `123.00` 之间闪。修法：判据改成**条的状态**（`bar_state in ('MAX', 'MAX_FADE')`），
   并且离开满费后再按满费格式多印 `FULL_COST_HOLD_TICKS = 12` 拍（8ms 一拍 ≈ 100ms），
   把 MAX / TRACK 边界上的偶发读错一拍吃掉。
2. **大数字那一格的宽度跟着文本走。** 原来是 `fr_rule.width = lb_frames.winfo_reqwidth()-8`，
   小数一出现格子就宽 71px。实测（修之前）：

| 大数字 | 数字格 | 白线 | 卡片宽 | 右列 x | 面板 reqw |
|---|---|---|---|---|---|
| `123` | 71 | 71 | 208 | 212 | 400 |
| `123.45` | 142 | 142 | 228 | 232 | 420 |

   面板每 8ms 在这两行之间来回跳 —— 看上去就是「抽一下」。

### 30.2 修法：预留宽度只跟「整数位数」走

* 预留按 **`整数位个 8 + '.88'`** 算（`8` = 30px，是这套数字里最宽的字形；拿 `0` 按 29px
  去算，最后一位会被切掉 6px）。白线按 `整数位个 8` 算 —— 按实际文本量的话，`123` 里那个
  细长的 `1` 和 `888` 差 30px，白线会跟着字形跳。
* **Label 的 `width=` 不能用**：它的单位是「字符」，Tk 拿字体的**平均宽**去乘（本机 40pt
  Bahnschrift = 30px），162px 的需求会被抬到 186px（白送 24px 空档），位数少时更亏。
  所以把 Label 钉成 `width=1` + `sticky='we'`，宽度交给
  `card.grid_columnconfigure(1, minsize=...)` —— 像素级精确。
  注意 minsize 管的是**整格** = 控件 + 右侧 `NUM_RIGHT_PAD`(13px)，漏掉就切字。
* 修之后实测（同一整数位数内**一个像素都不动**）：

| 文本 | 数字格 | 白线 | 卡片宽 | 右列 x | 面板 reqw |
|---|---|---|---|---|---|
| `0` | 115 | 56 | 180 | 184 | 400 |
| `123` | 175 | 82 | 240 | 244 | 432 |
| `123.45` | 175 | 82 | 240 | 244 | 432 |
| `888.88` | 175 | 82 | 240 | 244 | 432 |
| `1234.56` | 205 | 112 | 270 | 274 | 462 |

  位数真涨一位（99 -> 100）时白线和卡片一起变一次 —— 那是应该变的，游戏里那条压条本来就
  跟着费用位数变长。
* 拍图验证：把两次画面按像素相减，差异只出现在 `.45` 那三个字上（bbox 右缘 219 < 右列
  x=244），右边三行整块全黑。图在 `out/diag/小数抖动对比.png`（本机 150% 缩放，抓屏要用
  **物理**像素，逻辑坐标记得乘 2560/1707 ≈ 1.5，不然抓出来是桌面壁纸）。

### 30.3 那一行「状态」：删掉（2026-10-09）

先把毛病量化清楚：右列从窗口拿到的宽度是 `560 - 240(卡片) - 4 - 20 = 292px`，而状态行
最长的两条文案是 330px（满费提示）和 396px（「起锚」提示）。`_label()` 又没给 `anchor`，
tk 默认 `center` —— 超出部分**左右各切一半**，实测读出来是
`态 运行中（满费：按挂钟估，小数=不足一帧`，第一个「状」字都没了，而且切多少还会跟着
小数位一起变（就是上面那个「抖」的同一个来源）。改成 `anchor='w'` 只能算止血：从头开始
读了，尾巴照样少一截。

用户直接给了答案：「状态栏可以删掉」。于是这一行整个从面板上去掉，连带十几条写文案的
分支（运行中 / 已暂停 / 起锚 / 刚回费 / 相位重锚 / 不在关卡里 …）一起删掉：

* **跑动细节没丢**：下面「费用条」那一行本来就印着 `通道=`（pixel / clock）和 `模式=`
  （`res.mode` 原样打出来），满费走挂钟、暂停、帧操这些状态在里面都看得见。
* **告警没丢**：`res.warn` 一直打在「告警：」那一行。唯一**必须**保住的是看门狗那条
  「采样已停」（它是「数字不动」和「游戏暂停」长一个样时唯一的分辨依据，也是
  `tools/check_recover.py` 在断言的东西）—— 现在它写进「告警：」行并转红（`ERR`），
  没读到画面时把那一行清空。
* 窗口校准的进度文案原来是往状态行写的，现在并进「采样」那一行（`lb_perf`）。
* 副作用是好的：右列只剩两行（逻辑帧 / 游戏内时间），自然宽度 164px，面板内容宽
  240 + 4 + 164 + 20 = 428px < 560 —— **这一处溢出彻底没有了**，帧号涨到 5 位
  （卡片 300px，内容 488px）也还装得下。

## 31. 局内负费（费用数字左边那个减号）：判据、框、以及框为什么会偏（2026-10-09）

### 31.1 为什么非认出来不可

局内负费（可露希尔 / 忍冬那类机制）期间每个逻辑帧只攒**一半**的增量，于是一费从
30 个逻辑帧变成 60 个。**相位不重置**，转场那一帧补半个增量做亚帧修正。

不认出来的后果不是「少记一帧」：`_resync` 会按 1/30 的模型去挑整数 k，而真值是它的一半，
整段被数成**一半**（实测 300 拍只记 150 拍，见 31.5 的对照组）。判据只能来自像素 ——
费用数字左边那条纯白短横杠。

别和「回费速率」混：战前 tag（突袭 / 磨难 / 合约）把回费压到 -50% / -75% 时改的是
`required`（一费 60 / 120 个逻辑帧），**局内负费改的是 `speed`**（每帧的增量减半）。
倍速和子弹时间两个都不碰，它们走 `clock_scale`。

### 31.2 判据：三条，照抄前人

1. **纯白**：`> 250`（colorbar 的 `is_cost_sign_pixel`）。数字的抗锯齿边只是「亮」，
   凑不出一条长纯白横杠；
2. 这条纯白横杠要**连续够长**：`SIGN_MIN_RUN_UNIT = 21px`（前人 720p 实测 14px x1.5）；
3. **有一行满足就够**（720p 下减号的纯白芯只有一行高，分辨率越高越厚）。

阈值不是拍的：用户截图 `屏幕截图 2026-10-02 104850.png`（1905x1113）里，「22」这两个
数字最长的纯白横杠是 **18px**（阈值 21）—— 正常画面下留 3px 余量。面板上那行
「减号 run/thr」就是这两个数：认不出负费时，先看 run 离 thr 差多少，比猜阈值省事。

真负费录像 `Desktop 2026.10.09 - 22.36.10.14.mp4`（2560x1600 桌面录像、60.02fps、
1994 帧；这一局费用数字从 -4 走到 0，可露希尔那类机制）用真 `read_sign` 整段跑完：

| 段 | 帧数 | 最长纯白横杠 | 判定 |
|---|---|---|---|
| t=0.00..29.44（减号在） | 1768 | **41px** | 全部判负费，而且是**连续一段、零断点** |
| t=29.46..33.21（减号没了） | 226 | **7px** | 全部判非负费，**零误报** |

这一段 thr = 21 x 1.3333 = 28px：负费侧余量 1.46 倍（41/28），闲时侧只有 0.25 倍
（7/28）。判据和阈值都在真画面上对上了。

### 31.3 框：锚在**客户区**右下角（这一段是踩出来的）

四条边距（单位 = 1920x1080 基准，前人 1280x720 的实测值 x1.5）：

| 量 | 距客户区右边 | 距客户区底边 |
|---|---|---|
| 费用条槽 | 1u .. 180u | 267u .. 274u（中心 268u） |
| 减号框 | 105u .. 63u | 312u .. 301.5u |

u = scale x edge（`ui_edge_scale`）。**UI 缩放只乘「离锚点的距离」、不乘框本身大小** ——
和费用条、右上角那两个按钮同一个口径。换算成两个元素之间的关系更好记：
**减号框的中心在费用条中心上方 38.75u**（所以框要覆盖费用数字那一行）。

坑在这里：这个框锚的是**客户区**的右下角，而客户区不等于整幅画面。

* 实时读游戏窗口：画面就是客户区 -> 直接按宽高算（`layout_for`）；
* 桌面录像 / 播放器窗口里那段被缩放的画面：客户区带原点，还可能比画面小
  （实测 VLC 1378x844 的窗口里，1218x688 的游戏画面落在 (85,50)）—— 这时**必须**
  用 `reframe_layout` / `layout_from_bar_box` 平移过去的那一份。

第一版把 `sign` 做成了 `Layout` 的**派生属性**（每次读都按画面宽高算），于是平移过的那份
被丢掉，框整块偏到了别的地方。拿上面那段真负费录像（画面 2560x1600，游戏客户区
2560x1440 落在画面 (0,54)，条槽实测 240px，减号实测 x2422..2462 y1079..1083）
整段 1994 帧、两种锚点各跑一遍：

| 框 | 位置 | 判负费 | 最长纯白横杠 |
|---|---|---|---|
| 旧：按画面右下角算 | x2420..2474 y1184..1197 | **0 / 1768** | 0px |
| 新：跟着费用条走 | x2421..2476 y1079..1092 | **1768 / 1768** | 41px（阈值 28） |

旧框的 y 比真减号低了 **105px**（画面比客户区高 160px，这段全从底边漏掉了），整段
一个减号都没看见。x 只差 1px —— **错的是 y，是锚点，不是阈值。** 更早一版在另一段
录像（`2026-10-04 22-20-20.mp4`，2fps 抽 101 帧）上量到的是同一种偏移的另一种表现：
框落到「剩余可放置角色：N」那行纯白笔画文字上，101 帧里 36 帧误报成负费（36%）——
那行字和减号长得一模一样，所以这个坑不会自己露馅。

修法（三处，都在 `geometry.py`）：

* `sign` 从属性改成**字段**：`__post_init__` 只在它是 `None` 时按「客户区 = 整幅画面」
  兜底。为什么不用属性：`dataclasses.replace()` 会原样复制字段，属性则会按新的
  宽高**重算**（平移就白做了）；
* `layout_for` 按客户区算，`reframe_layout` / `layout_from_bar_box` 一起平移，
  `window.rescaled_layout` 一起缩放；
* 旧校准文件（`window_calib.json` / 录像缓存）里没有 `sign` 字段：`from_dict` 按
  **费用条**反推（`sign_from_bar`）—— 条在哪框就跟到哪，比按画面底边算准 50px 以上；
* `reframe_layout` 的裁剪顺手改严：客户区原点整个落在画面外时，原来会留下一个越界的
  空框（win32 / ffmpeg 只会悄悄裁掉），现在一律夹进画面。

`bar_only_layout`（画面被放大 / 裁剪，只拿到条框）同样按条反推 —— 那条路的客户区尺寸
根本推不出来，只有条是实测的。

`layout_from_bar_box`（录像链路 / 手动框选）也单独改了一处：sign 框改成**按框出来的
那条费用条反推**（`sign_from_bar`），不再用 `reframe_layout` 平移过来的那一份。理由：
平移那份的横向位置锚在「客户区右边」，而录像里客户区的宽（1920s）和原点都是**推**出来
的 —— 带着 `resolutions_measured.json` 里那条记录的推断误差（那段录像记录写着条槽右端
距客户区右边 7.53u，这段录像实测是 0.75u），于是框偏右 9px，正好是减号宽度的 20%。
条就在跟前，按它推（条槽右端 = 客户区右边 - 1u）更稳。同一段录像、同一帧（t=10，
减号在）实测：

| 用户框出来的条槽 | 平移那份 sign | 按条反推 sign | t=10 的 run（阈值 28） |
|---|---|---|---|
| 2320,1133 宽 240（正好） | x2430..2484 | x2421..2476 | 33 -> **41** |
| 2320,1133 宽 236（拖窄一点） | x2418..2472 | x2420..2474 | 41 -> 41 |
| 2320,1133 宽 231（再窄） | x2416..2469 | x2418..2470 | 41 -> 41 |

改完这一处，六种框选情况整段录像都是 1768/1768、零误报。这一组数字由
`tools/check_sign_box.py` 长期钉着（它比这些一次性量法更狠：连「擦掉减号之后会不会
被菱形 / 数字 / 那行字顶上来」都一起验了）。

### 31.4 手动档与面板上的证据

面板展开区有「局内负费」三档：**自动 / 强制开 / 强制关**（`settings.NEGATIVE_MODES`，
和「回费速率」存在同一份 json 里）。认错档能把整段拉回一半，所以留了强制档；
「减号 run/thr」那行是自动档下的原始证据。

### 31.5 回归项

* `tools/check_state_synth.py` 第 12 组：全负费 300 拍 = 300；正->负->正 420 拍 = 420；
  负->正 300 拍 = 300；转场正好压在回费边界上 400 拍 = 400；全负费 1800 拍里
  「61 帧的周期」只有 1 个（起锚相位让边界周期提前一格）。**对照组**（同一条信号抹掉
  减号）300 拍只记 150 拍 —— 差整整一半，这条最有说服力；
* `tools/check_sign_box.py`（本轮新加）：拿**真录像量出来的坐标**画一张假 HUD（满条 +
  数字笔画 + 菱形图标 +「剩余可放置角色」那行字），钉四件事 —— 两条真路（实时客户区 /
  录像框选）的框都必须把那 41px 的减号**横向整条**框进去、run 拿到 41；擦掉减号后
  run = 0（那些长得像减号的东西一个都不许顶上来）；**旧锚点当反例**，必须漏掉减号
  （实测框在减号下方 101px、run 19 < 阈值 28）；条挪 30px 框跟着挪 30px；
* `tools/check_boxpick.py` / `check_window.py` / `check_resolutions.py`：ROI 跟着客户区
  平移 / 缩放、越界一律夹进画面（假画面 + 真录像的 ROI 都要过）。这几条本来只盯着
  条 / 暂停 / 倍速三个，现在 `Layout.to_dict()` 里也带 `sign`，比对时会顺手把它钉住；
* `tools/check_ui_state.py`：减号框的 run/thr 读数不会把面板带崩。

### 31.6 还没做的

* **多位数负费**（-10 以上）：费用数字整串变宽会把减号往左推，而框的横向只覆盖
  单数字那一段的滑动范围（实测 -4 -> -3 时减号只挪 1px，位数一多就不是这个量级了）。
  遇到再量；
* 第 15 章某些敌方单位会让回费**提前停止**（条没走满就定住）：用户明确说先不处理；
* 子弹时间（`>>>`）下负费：**已验**（第 32.4 节的真录像回归）—— 条在动时走像素通道，
  与倍速 / 子弹时间无关，那一段逐周期 60 帧（负费真值）不漏；但满费 + 子弹时间
  要靠第 32 节那条规则（`>>>` 读不到时按 6 帧/秒算）。

### 31.7 量这段录像时踩的两个坑（记下来免得再踩）

* **抽流用的 `crop` 高度必须是偶数**：源是 yuv420p，写 `crop=280:95` 时 ffmpeg 实际按
  94 行输出（每帧 26320 字节），而按 280x95 = 26600 字节去读，每帧漂 280 字节，
  漂满一整帧的周期正好是 **94 帧 = 1.57 秒** —— 读出来一串「每 1.57 秒负费 0.3 秒」的
  假区间，看着特别像真信号（第一遍就是这么被骗的）。自检办法：`-f rawvideo` 落盘，
  字节数必须 = 帧数 x 宽 x 高，帧数 = 时长 x fps；
* **条槽满时只填到 236px，不是 240px**：1994 帧里填充最大 236px（右端 x2555），因为填满
  那一刻条立刻归零，末端 4px 是收边。所以**不能拿「最大填充」当条槽宽去反推 scale**
  （会得到 1.311，而真值是 1.3333）—— 这也是 `video.py` 的 `_measure` 必须在多个时刻上
  取并集、不能只看一帧的原因；
* 这段录像里 scale 卡不死的部分是诚实的：条槽 236（最大填充）..240px（客户区右边 2560
  减 1u）都能落在测量误差内，对应 1.311..1.3333。两种取法算出来的框都压在减号上
  （run 都是 41），所以对读数没有影响。


## 32. 满费 + 倍速键「整块空白」：按子弹时间算（用户 2026-10-10 定的规则）

### 32.1 现象：拖干员那两段，倍速键**整块没画**

`Desktop 2026.10.09 - 22.36.10.14.mp4`（2560x1600 桌面录像、负费 + 子弹时间，见第 31 节）
里有两段慢动作（7.0~16.5s、25.0~29.0s，条以 24~26 px/s 走 —— 负费 1/2 x 子弹 1/5
= 1/10，正好 6 逻辑帧/秒）。那两段里倍速键 ROI（x2091..2289 y92..250）里**只有场景**：

| 时刻 | ROI 单帧最亮 | 读数 |
|---|---|---|
| 12.0（拖干员） | **206**（场景） | digit_ratio 0.024、箭头带实心 0.046 |
| 18.5（1X） | 255 | digit_ratio 0.269、认成 1X |
| 29.5（2X） | 255 | digit_ratio 0.304、认成 2X |

也就是说用户看到的 `>>>`（他的原话「这里有三个三角」）**这一路读不到**：不是阈值调不对，
是那个框里画面上没有比场景更亮的字形（画着 1X/2X 时是 255，空白时最亮只有 206 的场景；
30 帧逐像素最大值合成也没有字形）。更糟的是**场景亮块**跑进了箭头带：整段 1994 拍里
有 **1277 拍**被判成子弹时间（实心占比恒 0.044~0.046，而真画着 1X 时是 **0.0000**），
而 `ARROW_SOLID_MIN = 0.020` 是从别的关卡量出来的（第 10 / 22 节：非箭头 max = 0.0113）
—— 在亮背景关卡上这条门不成立。

### 32.2 规则（用户给的）

**这一局里读到过倍速数字**（1X / 2X，判据是 `features.SpeedReading.has_digit`，
模板认不出也算「画着」）之后，倍速键再变成「什么都没画」就**按子弹时间算**：
恒 `BULLET_FPS = 6 逻辑帧/秒`（= 30/5，见 3.1），不再冻结。
从没读到过数字又读不到时仍旧冻结（宁可少记也不猜）。
这一路的 warn 单列 **`bullet-assumed`**（面板 / CSV 上看得见），
而且**绝不用 `last_m / 5` 去算**（2X 下那样会整段多记一倍）。

代码：`state.Counter._digit_seen`（进关卡读到数字后置位；`resync()` / 出关卡作废；
换布局时由 `adopt()` 带过去）+ `state.BULLET_ASSUMED_WARN`。

### 32.3 为什么必须带「读到过数字」这道门

「什么都读不到」还有另一条来路：**按钮淡出 / 被遮罩糊掉**。早期版本就是「没数字 = 子弹时间」，
结果一段 2 倍速录像里 **713 拍**被这样误判，白白少记 140 帧（56 秒里差 2.3 秒）
—— 见 `features.read_speed` 里那段注释。所以现在的门是：**这一局里见过这颗键正常画着数字**
之后才敢把「空白」解释成子弹时间。关卡外菜单 / 切场景的空白连 HUD（暂停键）和费用条都没有，
关卡判定先拦住了，走不到这一条。

代价仍旧说清楚：万一某次空白其实是按钮淡出而不是子弹时间，这一段会按 1/5 记，
比冻结**少记 5 倍**。所以 warn 是独立的 `bullet-assumed` —— 事后能按通道 / 时段统计
「哪一段、多少拍、加了多少帧」。

### 32.4 自检

* `tools/check_state_synth.py` 的 `bullet_assumed_at_max()`：四条 ——
  (a) 见过 1X 之后空白 -> 6 帧/秒 + `bullet-assumed`；
  (b) 见过 2X 之后空白 -> 还是 6 帧/秒（拿 `last_m/5` 算会是 12）；
  (c) 从没读到过数字 -> 0 帧 + `speed-unknown`；
  (d) 空白结束后画回 2X -> 恢复 60 帧/秒。
* `tools/check_speed_mix.py`：「满费+空白(见过数字)」= 330 帧（两段 1X 共 300 + 空白 5 秒 x 6），
  「满费+空白(没见过数字)」= 300 帧（中间 300 拍冻结）。
* 真录像回归：`22.36.10.14` 重喂一遍，通道分布、逐周期长度 `[60, 60, 60, 30]`、
  累计 286 帧（像素 286 / 挂钟 0）与改之前**逐位一致** —— 这条规则只在满费挂钟通道生效，
  条在动的时候碰不到它（也说明「负费 + 子弹时间」这一段本来就数对了）。

### 32.5 还没做的（下一步）

* **量出 `>>>` 的真实位置**：只要有一张「拖干员时右上角」的截图（或一段停住逐帧看的片子），
  就能把三个三角的坐标量出来直接认字形 —— 那就不用再靠「空白 + 读到过数字」这条推断。
  现在这条推断在**亮背景关卡**上还不够硬（见下一条）；
* 箭头带的 `ARROW_SOLID_MIN = 0.020` 在亮背景关卡上会被场景顶过去（实测 0.044~0.046）：
  要么换成「成块的形状」判据（连通域 / 三峰），要么干脆放弃这条判据、只留 32.2 的状态机。
  等 `>>>` 真坐标量出来再定。
